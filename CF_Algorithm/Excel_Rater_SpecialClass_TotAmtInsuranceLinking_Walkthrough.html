Wiring TotAmtInsuranceToUse into the Deductible Factor

A Special Class item's deductible band isn't always driven by its own Limit. When the item is linked to a specific building, ISO's own rule copies that building's combined total instead (Building + Contents + Special Class amounts). This walkthrough works through what that means for the live rater's existing architecture — Location Inputs for raw fields, CoreScratchpad for the real SUMPRODUCT/INDEX formulas, one calc tab per coverage.

Source: CommercialPropertySpecialClassRules.Rule.xml — SetTotAmtInsuranceToUse (line 2129), SetTotAmtInsurance (line 1049). Reviewed against CFRater1.01.xlsb read-only, 2026-09-14.

STEP 2 / 7

The item's own TotAmtInsurance — the fallback path

Confirmed by SetTotAmtInsurance: an item's own total, before any building-linking is considered, is just its own scheduled value.

Cell C7 — this item's own total, ignoring linkage for now
=IF(C_IncludedInBlkt="Yes", C_FullSpecialClassValue, C3)  ' C3 = this item's own Limit

Straight from the rule: TotAmtInsurance = FullSpecialClassValue if blanketed, else Limit. Nothing about building-linking enters into this cell at all — it's purely this item's own scheduled data. The blanket branch reads the same FullSpecialClassValue field already flagged as blocked in Excel_Rater_SpecialClass_InputWireframe.html's Mockup 2 — this formula can be built now, but it can't produce a real number for a blanketed item until that mechanism exists.

STEP 3 / 7

Building's own combined total is missing its third term

The blocking issue, found by reviewing CoreScratchpad directly — this has to be fixed before Step 4 can produce a correct number for linked items.

ISO's own definition (Building's rule, confirmed)
TotAmtInsurance = StructureLimitToUse + OccupancyTotAmtInsuranceSum + SpecialClassRiskTotAmtInsurance
                  '          (Building)              (Contents)              (Special Class -- the missing term)
CoreScratchpad's current combined-total cell (row ~137, "TOTAL LIMIT")
' as reviewed -- Building limit + Contents limit only, two of the three ISO terms
CoreScratchpad!C138 = Bldg_Limit + Contents_Limit
⚠This gap already existed before Special Class entered the picture — flagged previously as project memory project_deductiblefactor-uses-location-total-not-building-limit, and confirmed again on this review. It didn't matter in practice because nothing fed a Special Class amount into it. It matters now: a Special Class item linking to a building expects to read that building's full three-term total, but the cell it would read from is still only two terms.
STEP 4 / 7

Close the loop: sum linked items back into CoreScratchpad

One-directional linking (Special Class reads Building) isn't enough — Building's own total needs to gain a third term once Special Class items can link to it.

CoreScratchpad!C139 (new) — sum of every Special Class item linked to this building
=SUMPRODUCT(
  ('Special Class Item Inputs'!$LocationCol=CoreScratchpad!$LocationCol_ThisRow)*
  ('Special Class Item Inputs'!$IncludedInBuildingCol="Yes")*
  ('Special Class Item Inputs'!$LinkedBuildingCol=CoreScratchpad!$BuildingIDCol_ThisRow)*
  'Special Class Item Inputs'!$LimitCol)
CoreScratchpad!C138 (revised) — now the full three-term total
=Bldg_Limit + Contents_Limit + C139   ' third term now present
⚠Order of computation matters, but it's not circular. A Special Class item's own TotAmtInsurance (Step 2) never depends on this sum — only Building's total gains a term from Special Class, never the reverse. Compute Step 2 for every item first, then this SUMPRODUCT, then Step 5 below. No iterative/circular reference needed.
STEP 5 / 7

Resolve TotAmtInsuranceToUse per item

The actual branch from SetTotAmtInsuranceToUse, translated directly.

Calc_SpecialClass_BGI, one row per item
=IF(AND(C5="Yes", C6>0),
   ' linked -- pull the LINKED BUILDING's own combined total, not this item's
   XLOOKUP(C6, CoreScratchpad!$BuildingIDCol, CoreScratchpad!$C$138_PerBuilding),
   C7)   ' not linked -- this item's own total from Step 2

This is the one formula that actually decides which of the two paths from the source rule fires. Everything before this step (Steps 1–4) was building the two candidate values; this step picks between them per item, exactly the way SetTotAmtInsuranceToUse's own If/ Else does.

•Note this reads a per-building version of C138 — Step 4's revised total lives once per building, but a location can have several buildings (per the existing Locations_Buildings row-per-building layout already used by Building/Contents/BI). The lookup needs to key on the specific linked BuildingID, not just grab whichever building happens to be in the active row.
STEP 6 / 7

Wire into DeductibleFactorBasicGroupI

Same row-offset/INDEX pattern already used for Building's and Basic Group II's own deductible factors — only the AOI input changes.

Row offset within SpecialClass_DeductibleByLocationFactor_x_DeductibleFactorBasicGroupI.xlsx's 80-row table
=SUMPRODUCT(
  (DedFactorBGI!$A$2:$A$81=$C$2)*                        ' State
  (DedFactorBGI!$B$2:$B$81=$C$4)*                        ' Deductible
  (DedFactorBGI!$C$2:$C$81<$C$8)*                        ' C8 = resolved TotAmtInsuranceToUse, Step 5
  (DedFactorBGI!$D$2:$D$81>=$C$8)*
  (ROW(DedFactorBGI!$A$2:$A$81)-ROW(DedFactorBGI!$A$2)+1))
Resolved factor
=IF(C4="250", Deductible250Factor_Lookup,   ' shared, keyed "Basic" -- see the Coinsurance/Deductible workbook
   IF(C4="", 0,
      INDEX(DedFactorBGI!$E:$E, <row offset above>)))

This is exactly the shape Excel_Rater_BGII_DeductibleFactor_Walkthrough.html already established for Building's own tabs — a SUMPRODUCT row-offset into a pre-filtered table, then an INDEX pull. The only thing genuinely new here is the AOI input feeding the third and fourth conditions: it's Step 5's resolved value, not a plain Limit cell.
