Special Class — Own Tab, or Conditions on Building's Tab?

Written: 2026-09-14. Question: should Special Class Basic Group I rating be added into the existing Calc_Building_BGI workflow as conditional branches, or built as its own tab, following the pattern already used for Building, Contents, and Business Income? Basis: the factor-by-factor comparison in Excel_Rater_SpecialClass_HowItWorks.html.

Status: recommendation only, nothing built. Per standing project rule, nothing gets entered into the live workbook until you say go.
Recommendation
Own tab — Calc_SpecialClass_BGI — not conditions on Calc_Building_BGI

1. Why: the two coverages barely share any surface area

Building and Special Class share the general Rate → COLAdj → AdjustedRate → FinalRate shape — that's it. Below that shape, almost every column diverges:

One shareable row out of nine. Building conditions in would mean most of Calc_Building_BGI's columns carrying an if RatingType-equivalent branch just to go blank or 1.0 for Special Class rows — the same neutralization problem this project already had to work through for Specific/Tentative rating, except here it would apply to every column, not four.

2. It also breaks the pattern already established

This project already treats "coverage" as the tab boundary, not "form" or "rating variant": Calc_Building_BGI, Calc_Contents_BGI, and Calc_BusinessIncome_BGI are one tab per coverage. Within a single coverage's tab, conditions are the right tool when the branches genuinely share a rating key and most of the downstream chain — that's exactly what Building's own Class-vs-Specific/Tentative branch does, because both paths read the same ClassCode/ConstructionCode-adjacent columns and the same downstream COL/coinsurance/deductible steps.

Special Class doesn't meet that bar. It's a sixth core coverage with its own rating key, not a rating variant of Building. Folding it in as conditions would be the first place in the workbook where "conditions" stops meaning "same shape, different rate source" and starts meaning "different coverage wearing Building's column headers."

Net: the own-tab cost is small and one-time (a tab, two columns); the conditions cost compounds across nearly every row of an existing, already-built tab. That asymmetry is why the recommendation leans firmly toward a new tab rather than presenting this as a close call.

4. What the new tab would look like, at a glance

  • Calc_SpecialClass_BGI — same shape as the other three coverage tabs: one row per scheduled Special Class item, Rate → COLAdj → AdjustedRate → FinalRate, feeding its own premium branch in Premium_Summary.
  • New Locations_Buildings (or an item-level equivalent, if Special Class items don't map 1:1 to buildings) columns: ClassDescription, and confirmation that the existing ProtectClass input can be read directly rather than re-entered.
  • Reads shared, already-existing inputs for everything else — Coinsurance/BlktCoinsurance, Deductible, Limit/BlktLimit, IncludedInBlkt, Bldg_VandalismExcluded, Bldg_StdPropertyPolicy, and the policy-level LCM/ PackageModFactor/MultiPremiumAndDispersionCreditFactor/IRPMFactor — see Excel_Rater_SpecialClass_HowItWorks.html §5 for the full input-field breakdown.
