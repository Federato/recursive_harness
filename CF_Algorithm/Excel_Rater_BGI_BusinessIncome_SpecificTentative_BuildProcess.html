Companion to Excel_Rater_BGI_SpecificTentative_BuildProcess.html (Building) and Excel_Rater_BGI_PersonalProperty_SpecificTentative_BuildProcess.html (Contents) — read those first for the base pattern; this page only calls out where Business Income diverges from it.

1. What's different here, in plain English

Business Income's Basic Group I chain is only 3 steps where Building's is 8 — because for the Class-rated path, Business Income doesn't compute its own base rate at all. It cross-references Calc_Building_BGI.BaseRate, the value Building's own tab already looked up for the same structure. Rate the Building first; Business Income is arithmetically downstream of it.

That borrowing stops under Specific/Tentative rating. The source doc is explicit about this: "Note what this branch does not read: Calc_Building_BGI.BaseRate." Under Specific/ Tentative rating, Business Income substitutes its own SpecificGroupIRate directly — same pattern as Building and Contents, no cross-tab dependency for this branch specifically.

Two more things make this coverage's version of the formula its own shape, not a copy of Building's or Contents': an extra multiplier neither of the other two coverages has at all, and a downstream chain that's genuinely shorter regardless of which rating path produced Rate.

One more branch, and it's genuinely unresolved — not just a naming difference. Building has a confirmed third Otherwise → 1.0 branch for any RatingType value besides Class/Specific/Tentative. Contents has a confirmed broad ≠ "Class" gate with no catch-all at all. Business Income's source doc shows only three branches — the blanket/max-period aggregate, Class, and Specific/Tentative — with no fourth branch documented either way. Don't assume it matches Building's 1.0 fallback or Contents' "runs anyway" behavior — treat this as a genuinely open question, not settled by analogy to its siblings, until the ISO rule XML is checked directly.
The blanket/max-period branch takes priority over both rating types. Before Rate even checks RatingType, it first checks whether BI_MaxPeriod = "Y", BI_MonthlyLimitOfIndemnity <> "Not Applicable", or BI_CovType = "Extra Expense Only" — combined with BI_BldgIncludedInOperationalUnit = "Y". If that combination holds, an entirely different aggregate formula fires (HighestBusnIncomeBasicGroupIBaseRate × BGIBaseRateAdjustmentFactor, not built this pass) regardless of whether the building is Class- or Specific/Tentative-rated. This isn't part of the neutralization grid above — it's a gate that sits in front of the whole Class-vs-Specific question.

3. Before you build anything: the open questions

BI_SpecificGroupIRate carries the same open question as Building's and Contents' versions. No Set or Lookup rule populates it anywhere in the Business Income rating-algorithm doc either. Same best-supported-but-unconfirmed guess: a user- or schedule-entered value. Build it as its own column with the same open-question comment — don't reuse Building's or Contents' column, and don't assume the three values match for the same building.

The missing fourth branch (see the note above) is a second open question specific to this coverage — treat it as unresolved rather than defaulting it to either sibling coverage's behavior.

Rate =

    elif RatingType = "Class":

Everything after Rate — COLAdj, Factor, FinalRate — is already built and needs no changes. It reads whichever Rate this branch produced, same as it already does for the Class-rated path.

Step 4 — Nothing changes in Premium_Summary

The BI_BGI_Premium formula in §5 of the source doc reads Calc_BusinessIncome_BGI.FinalRate regardless of which rating path produced it. No new formula needed.

5. Test cases to build alongside the formula

  1. A building with RatingType = "Class" — confirms the new branch doesn't disturb the existing path, and that it still correctly reads Calc_Building_BGI.BaseRate.
  2. A building with RatingType = "Specific" and a BI_SpecificGroupIRate entered — confirms the new branch fires, does not read Building's BaseRate, and downstream COLAdj/ Factor steps still apply correctly.
  3. A building with RatingType = "Tentative" — should produce the identical result to the "Specific" row above with the same inputs.
  4. A building where the blanket/max-period condition (BI_MaxPeriod = "Y" etc., plus BI_BldgIncludedInOperationalUnit = "Y") is also true, with RatingType = "Specific" — confirms the blanket/max-period branch correctly takes priority and the Specific/Tentative formula never fires, since that branch isn't built this pass and shouldn't silently fall through to it.
  5. A building with a non-trivial BasicGroupIRatingTerrFactor and ProtectionClassFactor on the Class-rated row for the same building/location — flip to Specific and confirm the workbook drops them (per the §2 grid) rather than carrying them through from a stale reference.
  6. A building with some other/blank RatingType value — do not assume an expected result for this one. Flag it in review as the open question from §3; whatever the workbook currently does with it (falls to Class, falls to Specific/Tentative, produces an error, or something else) needs to be checked against ISO's rule XML before being treated as correct.

6. How to configure this once built

  1. On Locations_Buildings, find the row for the building in question and set RatingType to Class, Specific, or Tentative — this is the same switch Building's and Contents' branches already use.
  2. If you set it to Specific or Tentative, fill in BI_SpecificGroupIRate with the rate you were given for Business Income specifically — do not reuse the Building or Contents value, even if they happen to look similar for this risk.
  3. Leave everything else on the row exactly as you would for a Class-rated building — the coinsurance/type-of-risk Factor step and the limit still apply the same way.
  4. Check Calc_BusinessIncome_BGI for that row: Rate should now reflect the Specific/Tentative formula instead of the borrowed Building rate, and COLAdj/Factor/ FinalRate should populate normally from it.
  5. If the resulting premium looks wrong, check BI_SpecificGroupIRate first — same caveat as the other two coverages, this workbook cannot detect a wrong hand-entered rate the way it might catch a bad table lookup.
