CF_Algorithm · Commercial Property · Special · Contents Build Plan

Building is done. What does that actually buy Contents?

Building's full 9-step chain is built, live-wired, and audited (Excel_Rater_Special.md §0). Contents is a genuinely different, longer chain (14 steps) — richer, not a rename. This page sorts Contents' needs into three honest buckets: what transfers as-is with zero new work, what needs a new data pull but no new mechanism, and what needs both. The goal is the cheapest real path through it, not a false shortcut.

2

Direct reuse — zero new tables, zero new pulls

These two steps can be wired for Contents today, off tables that already exist on BldgSpecialRating.

DeductibleByLocationFactor (Contents step 1)
Per Excel_Rater_Special.md §5 step 1, this is Copy'd from an ancestor in ISO's own rules — the source doc already says to build it as "the same local logic Building's tab uses." Building's own version is itself a simplification: =C19, a direct copy of BGI's already-computed DeductibleByLocationFactor cell, since the underlying table (DeductibleByLocationFactor, State|CW,"Y", flat 0.995, zero state variation) and gate are the same regardless of form. Contents can copy the exact same cell — =C19 again, or equivalently =[Building's Special row 89] once that's live. No new table, no new CoreScratchpad block.
DeductibleFactor (Contents step 2) — the real prize
Per Excel_Rater_Special.md §5 step 2: "this one is genuinely computed locally in ISO's own rules, the only deductible factor of any Contents form that is." Same four-branch shape as Building's step 8, same two tables (DeductibleFactor "Other Cause Of Loss" slice, Deductible250Factor causeOfLoss="Special") — already pulled, verified, and live in Special_DeductibleFactor.xlsx / BldgSpecialRating!W:AE. The only differences: Contents keys the theft-branch gate on SpecialTheftExclusionIndicator = 0 instead of reading TheftExclusionAttached directly (same underlying concept, different field), and reads OccupSpecialTotAmtInsurance-family limits instead of the Building-scoped ones. The lookup tables themselves don't need to move or be re-pulled — Contents' CoreScratchpad block just needs its own row offset/INDEX chain pointing at the same W:AE range, fed by Contents' own State/Deductible/Limit inputs instead of Building's.
⚠Both of these still carry Building's own documented simplifications forward: DeductibleByLocationFactor borrows BGI's Per Location Deductible gate rather than a true theft-specific one, and DeductibleFactor's Branch 1 (separate theft deductible) can't be built until TheftDeductible exists as its own field on Location Inputs — same gap Building has, not a new one Contents introduces.

⚠Don't assume these follow Building's happy pattern. Building's own SpecialBuildingRate looked CW-header-only and turned out to resolve in 45 of 46 states once pulled per-state — but that's not a guarantee these four will too. SpecialPrsnlPropRate and SpecialPrsnlPropTheftExclusionFactor are occupancy-keyed, a structurally different (and historically thinner-filed) kind of table than the flat State|"Y" tables that turned out fine for Building. Pull and check before assuming either way — same discipline this project applied to SpecialBuildingRate and to FL's residential/non-residential mechanism.
✓One shortcut worth taking: BroadSpecialLOIFactorPrsnlProp is shared with Broad's own Contents chain (same relationship Building's BroadSpecialLOIFactorBldg has with Broad's Building chain, already confirmed and reused). Pulling this table once unblocks both Broad's and Special's Contents LOIFactor steps — same leverage Special_LOIFactor_Bldg.xlsx already got from Broad's Building pull.
5

Schedule-copied fields — not rate tables at all

PP_WatchmanCreditFactor and PP_BurglaryAlarmCreditFactor, per Excel_Rater_Special.md §3: "not rate-table lookups — copied directly from the insured's protective-safeguards schedule entry." No Rate_Tables block, no CW/state pull, nothing to verify against ISO filings.

WatchmanCreditFactor = PP_WatchmanCreditFactor       if SpecialTheftExclusionIndicator = 0 and PP_ProtectiveSafeguardsOnFile = "Y"
    else: 1.0

BurglaryAlarmCreditFactor = PP_BurglaryAlarmCreditFactor   (same gate as above)

The only prerequisite is adding PP_ProtectiveSafeguardsOnFile, PP_WatchmanCreditFactor, and PP_BurglaryAlarmCreditFactor as fields on Location Inputs — user-entered values off the insured's own schedule, the same category of gap as the still-missing Coverage Type, TheftDeductible, and Builders Risk reporting-form-limit fields Building already flagged. Cheapest of the four remaining gap-classes to close, since there's no ISO data to pull at all — just three new input rows.

Easiest path through it, in order

Ordered by cheapest-to-most-expensive, not by ISO's own step numbering.

OrderStepWhy here
1Wire DeductibleByLocationFactor and DeductibleFactor (§2)Zero new data. Same tables Building already has live and audited — this is copy-the-pattern, not build-something-new. Closes 2 of Contents' 12 steps immediately.
2Add the three schedule fields (§5) and wire WatchmanCreditFactor/BurglaryAlarmCreditFactorNo ISO data to pull, no table to verify — just new Location Inputs rows and a two-branch IF. Closes 2 more steps.
3Pull and row-count BroadSpecialLOIFactorPrsnlPropUnblocks Broad's Contents LOIFactor at the same time — the one new pull with a second beneficiary.
4Pull and row-count SpecialPrsnlPropRate, SpecialPrsnlPropTheftExclusionFactor, PrsnlPropTerrMultiplierThe real unknowns — do these last precisely because they're unverified; don't let easy wins upstream create false momentum before the hardest, most uncertain part is actually checked.
5Wire Rate, COLAdj, AdjustedRate, FinalRate (§3)Pure arithmetic once every input above resolves — the CoreScratchpad pattern is already proven, this is assembly, not discovery.
7

What this doesn't cover

Same exclusions Building's own build carried, plus one Contents-specific one.

Legal Liability and blanket premium branches — out of scope for both coverages, per Excel_Rater_Special.md §7. Worth re-flagging Contents' own wrinkle here: its Legal Liability branch uses SpecialCauseOfLossAdjustment (already theft-adjusted), not the raw rate Building's branch uses — a real formula divergence, not a naming one.
The theft-specific branches (Building's DeductibleFactor Branch 1, Contents' equivalent) — both need TheftDeductible as its own field, still absent from Location Inputs.
The combined-location-total correction (SpecialTotAmtInsurance / OccupSpecialTotAmtInsurance vs. Building-limit-only) — deliberately backlogged project-wide until Contents exists to make the gap visible, per project memory. Building this out for Special's Contents is actually the point at which that backlog item becomes concrete and fixable, not just theoretical.

Remaining steps

  1. Sections 2 and 5 above are buildable with zero new ISO data — the cheapest possible next session on this form.
  2. Section 4's three unverified occupancy/territory tables are the real open question for Contents, and per §6, deliberately last in the recommended order, not first — resolve them once, not twice.
  3. Nothing gets built until you say go.
