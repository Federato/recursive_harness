Legal Liability vs Class / Specific — Building

Written: 2026-09-16. Source: CommercialPropertyStructureRules.Rule.xml and CommercialPropertyStructureBuildingBasicGroupICoverageRules.Rule.xml (CW 20260601 V01), read directly. Companion page for Personal Property: Excel_Rater_LegalLiability_vs_ClassRated_PersonalProperty.html — the two mechanisms are not the same, despite the shared table.

Status: traced, not built. Legal Liability sits at "formula only" for Building in Excel_Rater_CoreCoverages_RatingGrid.html.

1. The one-sentence version

The rate chain is identical. The premium formula is not. Legal Liability runs the same base rate, the same territory, protection class and cause-of-loss adjustment as any Class-rated building — and then the premium formula picks the rate up three steps earlier than the Class-rated branch does, throwing away the limit, coinsurance and deductible layer entirely, and multiplies in two factors that exist nowhere else.

Where the fork actually is. Not in SetBGIRatesAndFactors. Not in SetFinalRates. It is a Choose branch inside SetPremium, in the coverage file. Everything upstream of that branch is shared code that has already run.

4. The two factors that only exist here

FactorMatrixKeysCW values
LegalLiabilityFactorLegalLiabilityFactor State + the literal "Bldg" 0.25. The table's only other row is PersProp at 0.50 — the Personal Property side reads it. Two rows, one table, two coverages. No state files its own.
LegalLiabAddlInsurableIntFactorAddlInsurableInterestFactor State + AddlInsurableIntOption off the Legal Liability Coverage Form record Option1 1.25 · Option2 1.25 · Option3 1.0 · Option4 1.0. No state filings.
The trap: a missing option zeroes the premium. SetLegalLiabAddlInsurableIntFactor requires all three of — CovType is Legal Liability, a CommercialPropertyLegalLiabilityCoverageForm record exists, and AddlInsurableIntOption is non-blank. Fail any one and the factor is set to 0.0, not 1.0. Since the Legal Liability premium multiplies by it unconditionally, a Legal Liability item with no additional insurable interest elected produces a premium of zero. Options 3 and 4 are already 1.0, so a neutral value exists in the table — the rule just doesn't reach for it. Reproduce the 0.0 as filed; do not "fix" it to 1.0 in the rater without a circular check.

Read the zero-premium default correctly. Option4 is “None”, and it returns 1.00. So a risk with no additional insurable interest is meant to be coded as Option4 and gets a neutral factor. The 0.0 fires only when the field is left blank, or the Legal Liability Coverage Form record is missing altogether — in other words this input is mandatory once Legal Liability is selected, not optional with an unfortunate default. Build it as a required field with the four options, and keep a check cell for the blank case.
The option mapping is not in the current edition. DomainAddlInsurableIntOption — the table that maps the plain-language selection to Option1–Option4 — is header-only from the 20221001 package onward. The only edition carrying the mapping is 20191201. The plain-language list itself (DomainAddlInsurableInt) is still current. Pull the mapping from the 2019 package; do not conclude it does not exist because the current package ships it empty.

Which of the eleven actually move money. Given the same election on the same risk, only two change the number: #3, the 0.25 vs 0.50 factor, and #6, Special's rate source — Building drops the theft-exclusion credit and the roof-surfacing ACV factor, Contents keeps the theft credit. Both of #6's factors default to 1.0, so it bites only on an endorsed risk. #8 is equal by construction today (Contents seeds its local Limit from ../Limit) and is a latent risk rather than a live difference. The remaining eight are wiring: they change how you build it, not what it costs.
Identical on both sides. The two Legal Liability factors and their tables (AddlInsurableInterestFactor: Option1 1.25 · Option2 1.25 · Option3 1.0 · Option4 1.0, countrywide, no state filings) · no coinsurance, LOI or deductible factor · no MultiPremiumAndDispersionCreditFactor · rate side rounds to 3 dp and money side to 0 dp · cyber factors applied outside the rounding · a blank AddlInsurableIntOption forcing the factor to 0.0 and the premium to zero.
How Legal Liability actually gets selected — and it is not the same act on the two coverages.
  • Building: CovType is set on the building item itself. One item can be Legal Liability while the item beside it is Building or Builders Risk.
  • Contents: SetCovForm is a plain Copy of ../../CovForm, and ../../ from the Personal Property record resolves to CommercialPropertyOccupClass. The choice is made once at the occupancy class and every contents item beneath it inherits it — there is no per-item override, so Legal Liability and Building-and-Personal-Property contents cannot be mixed inside one occupancy class.
The list itself is DomainCovForm, keyed State + PolicyType + RatingType, six entries: Building and Personal Property · Condominium Association · Condominium Commercial Unit Owners · Legal Liability · Tobacco Sales Warehouse · Class Rated Building Only. Two constraints fall straight out of the keys: Legal Liability is offered on a Commercial Property Policy only (the Standard Property Policy rows do not include it), and it is available under Class, Specific and Tentative rating types — it is not confined to class-rated risks.

This is also why the additional-insurable-interest record sits at occupancy-class level on the Contents side (difference 5): it is at the same level as the form choice, which makes the pair consistent rather than arbitrary.

For the rater: a dropdown per building item drives Building; a single dropdown per occupancy class drives every contents item under it.

7. Blanket, and why Legal Liability never reaches it

SetPremium is a Choose, so the first matching branch wins. The Legal Liability test sits at branch 2; the blanket test sits at branch 3. A Legal Liability item marked IncludedInBlkt = "Yes" still matches branch 2 and rates as scheduled — BlktBasicGroupIAvgRate is never consulted.

Whether that is intent or an ordering accident is a manual question, not an ERC one. What matters for the build: do not add a blanket path to the Legal Liability column. It cannot be reached.

9. What to build

  1. Do not branch the rate chain. Every rate row through BasicGroupICauseOfLossAdjustment is shared — point at the cells you already built.
  2. Branch at the premium row only, on CovType = "Legal Liability".
  3. Two new lookup blocks, both tiny and both countrywide: a 2-row LegalLiabilityFactor and a 4-row AddlInsurableInterestFactor. Pull the plain-language→Option mapping from the 20191201 package; the current one ships it empty.
  4. Build all four forms. The premium shape is identical; only the rate datadef changes. Broad takes BroadRate and Special takes SpecialRate — both raw, neither a cause-of-loss adjustment.
  5. Reproduce the 0.0 defaults on both factors, and add a visible check cell so a zero premium is obvious rather than silent.
  6. Leave the blanket cell empty for this CovType, and leave Leasehold Interest out of this file entirely.
