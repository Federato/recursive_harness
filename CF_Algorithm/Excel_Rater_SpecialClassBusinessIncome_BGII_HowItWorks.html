How Special Class Business Income Basic Group II Rating Works

How Special Class Business Income Basic Group II Rating Works

Written: 2026-09-16. Source: CommercialPropertySpecialClassBusnIncomeRules.Rule.xml and CommercialPropertySpecialClassBusnIncomeBasicGroupIICoverageRules.Rule.xml (CW 20260601 V01), read directly this session, plus an all-batch sweep of every rate table below at each state's adopted edition. Companion to the Basic Group I page on the same datadef group.

Status: traced, not built. No Business Income rows exist on Special Class Worksheet. Basic Group I's wiring (steps 1–8 of the BGI formulas page) is the prerequisite — BGII reuses its Factor and its premium shape.

1. What's different about this chain, in plain English

Basic Group II does its own lookup. Basic Group I did not. On the BGI side, step 1 was a straight Copy of the parent Special Class item's already-computed rate. Basic Group II instead runs a real matrix lookup against BasicGroupIIRate.

But every key it looks up with is borrowed. Territory, symbol and the class hazard number are all read two levels up from the coinsured Special Class item (../../). Business Income contributes no dimension of its own to the base rate — it contributes the same single time-element Factor that Basic Group I contributes, and nothing else. So "does its own lookup" describes the plumbing, not the pricing: the numbers are still the building's.

The thing most likely to be built wrong: this chain has no BCEG factor, no Builders Risk factor and no Standard Property Policy factor. All three appear in at least one sibling Basic Group II chain, and none of them appears here. See section 7 — the temptation is to copy a sibling's formula and inherit a multiplier that Special Class Business Income does not apply.

2. The rating chain, step by step

SetBGIIRatesAndFactors is four steps.

#StepWhat it does
1SetBasicGroupIIBaseRate Gated on ../../BasicGroupIIRatingTerr and ../../BasicGroupIISymbol both non-blank. If either is blank the base rate is 0.0. Otherwise LookupBasicGroupIIRate(State|CW, ../../BasicGroupIIRatingTerr, ../../BasicGroupIISymbol, "Bldg").
2SetLowestBasicGroupIIBaseRate Same shape, one key shorter — LookupLowestBasicGroupIIRate(State|CW, ../../BasicGroupIISymbol, "Bldg"). No territory. Only ever used by step 4's second branch.
3SetBasicGroupIIRate BasicGroupIIBaseRate × LossCostMultiplier × ../../BasicGroupIINumericValue, rounded to 3 decimals at both products.
4SetBasicGroupIICauseOfLossAdjustment Two branches on whether a wind/hail exclusion record exists — see below.

Step 4, written out

no CommercialPropertyWindstormOrHailExclusionSpclClassBusnIncome record:
    BasicGroupIICauseOfLossAdjustment = BasicGroupIIRate            <- straight Copy, nothing applied

otherwise:
    BasicGroupIICauseOfLossAdjustment =
        LowestBasicGroupIIBaseRate x LossCostMultiplier x WindstormOrHailExclFactor

The excluded branch does not discount the rate you just built — it rebuilds it from the lowest base rate and never refers to BasicGroupIIRate at all. Note what that discards: ../../BasicGroupIINumericValue is in the normal rate and absent from the wind/hail-excluded rate. Excluding wind and hail therefore drops the class hazard load as a side effect.

Accepted simplification — logged, not fixed. ISO files two wind/hail exclusion records: …WindstormOrHailExclusionSpecialClass on the building item and …WindstormOrHailExclusionSpclClassBusnIncome on this group. The lookup is genuinely shared (same matrix, same single key, and this group reads the key off the building item anyway) — only the gate differs. The rater points Business Income at the Special Class building's WindstormOrHailExclFactor cell, so a risk cannot exclude wind/hail on one and not the other. Decided 2026-09-16. Tracked as S-2 in Rater_Simplifications_Backlog.md, alongside the identical vandalism case (S-1).

The premium file is the Basic Group I premium file with the datadef names swapped — same hardcoded CoverageOnPolicyIndicator = 1, same two branches, same double round(…, 0), same seven-level climb for the policy factors. Nothing about Group II's premium is distinctive.

4. Shared factors — what this chain reads rather than computes

Eleven values feed the Basic Group II premium. Three are computed inside the Special Class Business Income group. The rest are read from somewhere else, and the rater should point at those cells, not recompute or copy them.

ValueScopeWhere it is setWho else reads the same value
BasicGroupIIBaseRate, LowestBasicGroupIIBaseRate, BasicGroupIIRate ownThis group, steps 1–3Nobody — local to this chain
../../BasicGroupIIRatingTerrborrowed The parent Special Class item Special Class Building's own BGII chain. One resolution, two consumers.
../../BasicGroupIISymbolborrowed The parent Special Class item Special Class Building BGII, and this group's own WindstormOrHailExclFactor lookup. Used as a key in three places.
../../BasicGroupIINumericValueborrowed The parent Special Class item, resolved by ClassDescription via SpecialClassBasicGroupIINumber — not by ClassCode Special Class Building BGII. Business Income never recomputes the class hazard load.
LossCostMultiplierborrowed SetLossCostMultiplier is a straight Copy of ../../LossCostMultiplier — the parent Special Class item's, not one of its own Every form in this group — BGI, BGII, Broad, Special, EQ — and the parent item itself
WindstormOrHailExclFactorown This group's SetWindstormOrHailExclFactor, keyed on the parent's symbol Set per datadef group, but off a shared table and a borrowed key — see section 4
Factorshared within group SetFactor — one four-way Choose, computed once Basic Group I and Basic Group II only. Broad, Special and Earthquake never multiply by it. Build it once and point both rows at it.

CyberIncidentExclusionCOLExcptnsFactorBusnIncomeBGIIToUse coverage-family This group, from the policy-level …COLExcptnsFactorBGII The Business-Income family only. Property-damage coverages read CyberIncidentExclusionCOLExcptnsFactorBGII instead — different datadef, do not cross-wire.

The rule of thumb. If a value is set at DataDefGroup="CommercialProperty" or read with ../, it is one value with many readers, not a per-coverage value that happens to agree. In the workbook that means a cell reference. Two cells holding 0.995 today is the failure mode — a circular changes one and the copy diverges silently.

The blocker, stated plainly. BasicGroupIIRate and LowestBasicGroupIIRate hold no countrywide rows at all. Unlike every other table on this page there is no CW fallback to lean on — the state row is the only row. A rater that pastes "the CW table" for Basic Group II pastes an empty range. All 45/39 state tables have to be loaded, and FL and PR have to be handled as "cannot rate Basic Group II" rather than as a lookup miss returning zero.

6. What is genuinely this group's own

  1. The three rate datadefs in steps 1–3.
  2. The decision to gate on the parent's territory and symbol, defaulting to 0.0.
  3. The wind/hail branch choice — rebuild from lowest base rate rather than discount.

Everything else on this page is borrowed, shared, or policy-level.

8. What to build, in order

  1. Finish Basic Group I first. Factor and the premium shape come from there; BGII adds no new machinery to either.
  2. Load the two Basic Group II base-rate tables per state. This is the real work — 45 and 39 state tables, no countrywide fallback. Expand every state into its own rows.
  3. Point, do not copy, at the parent Special Class item for territory, symbol and numeric value, and at the policy level for the cyber, IRPM and package-mod factors.
  4. Handle FL and PR explicitly as "no Basic Group II base rate filed" rather than letting a missing lookup fall through to zero — a silent zero here reads as a free coverage.
  5. Flag the 8 no-lowest-rate states (AR, DC, FL, KS, NY, PR, RI, TX) on the wind/hail-exclusion path for the same reason.
