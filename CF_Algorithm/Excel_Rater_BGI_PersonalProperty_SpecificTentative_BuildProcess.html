1. What this is, in plain English

Same escape hatch as Building's: Basic Group I is the only Commercial Fire form where a building's contents can be rated off a pre-set rate instead of ISO's class/construction tables. Class rating looks up a rate keyed on the item group and construction; Specific/Tentative rating substitutes a single number someone else already decided on.

Contents' version of this isn't a copy of Building's — the gate is written differently, one factor's own definition changes value depending on RatingType in a way that matters for how you build the formula, and there's no fallback branch for stray values the way Building has one. Those differences are the point of this page.

2. The rating grid — every Personal Property factor, Class vs. Specific/Tentative

Same method as the Building grid: of every factor that feeds a Class-rated Contents row's FinalRate, which ones still apply under Specific/Tentative rating, and which ones don't?

Assumption applied in this grid: where the source doesn't clearly state a rate or factor applies, it's treated as neutralized — 1.0 for a multiplicative factor, 0 for an additive addend — rather than assumed carried over. That's a stated assumption, not a confirmed ISO rule, called out per row.

Reading this grid: rows 3, 5, and 6 (red) are where the neutralization assumption applies — the source formula omits them with no stated value. Row 4 (amber) is a different kind of case: not an assumption, a confirmed fact about the column that only matters if the workbook is built carelessly (see the note below). Rows 1, 2, 7–16 (green) are directly confirmed by the source text either way. The two gray rows are structural absences that have nothing to do with rating type at all — they were never part of any Contents formula.

Build risk on row 4 — don't share the FireSafeVaultFactor cell across branches. If Calc_Contents_BGI is built with one shared FireSafeVaultFactor column that every Rate formula references — Class-rated and Specific/Tentative alike — then this column's own confirmed 0.0 value under RatingType ≠ "Class" would silently zero out the entire Specific/Tentative Rate if that branch's formula accidentally multiplies by it. The source's own Specific/Tentative formula never references FireSafeVaultFactor — build the two branches as genuinely independent formulas (per the if/elif block in §5 below), not as one formula sharing every intermediate column.
The gate is broader than Building's, and there's no catch-all. Building's Specific/Tentative branch only fires on RatingType exactly "Specific" or "Tentative", with a third Otherwise branch flattening anything else to Rate = 1.0. Contents has no such catch-all — its gate is RatingType ≠ "Class", so any non-Class value (including a blank or a typo) runs the Specific/Tentative formula, not a flat 1.0. Don't copy Building's three-way branch onto Contents; it would introduce a fallback that doesn't exist in the source.

3. Before you build anything: the one open question

PP_SpecificGroupIRate — the rate itself — is not populated by any rule in the traced source document, same as Building's version. No Set rule, no Lookup rule. The source docs never say where the number comes from.

Same best-supported guess as Building: it's a rate an underwriter or MGA schedules by hand for that specific risk — an inference from the term, not a confirmed fact. Treat this as unresolved until someone checks the actual ISO rule XML. Build it as a user-entered field, flagged visibly, not a Rate_Tables lookup.

5. Test cases to build alongside the formula

  1. A location with RatingType = "Class" — confirms the new if doesn't disturb the existing path.
  2. A location with RatingType = "Specific" and a PP_SpecificGroupIRate entered — confirms the new branch fires and downstream steps still apply correctly.
  3. A location with RatingType = "Tentative" — should produce the identical result to the "Specific" row above with the same inputs.
  4. A location with some other/blank RatingType value — Contents should still run the Specific/Tentative formula, not fall to a flat value the way Building does. This is the case most likely to get built wrong by copying Building's three-way branch onto Contents.
  5. A Specific-rated item with a non-trivial ProtectionClassFactor and TerritoryFactor on the Class-rated row for the same item — confirm the workbook actually drops them (per the §2 grid) rather than carrying them through from a stale formula reference.
  6. A Specific-rated item where the location's CovType would otherwise trigger the fire-safe-vault 0.50 discount if Class-rated — confirm the Specific/Tentative Rate comes out unaffected by that discount either way (neither the 0.50 nor the confirmed 0.0 from row 4), proving the two branches are truly independent formulas per the build-risk note in §2.

6. How to configure this once built

  1. On Locations_Buildings, find the row for the location in question and set RatingType to Class, Specific, or Tentative.
  2. If you set it to Specific or Tentative, fill in PP_SpecificGroupIRate with the rate you were given for that risk's contents — typed in by hand, not looked up (see §3).
  3. Leave everything else on the row exactly as you would for a Class-rated location — deductible, coinsurance, limit, and all the other columns still apply the same way.
  4. Check Calc_Contents_BGI for that row: Rate should now reflect the Specific/Tentative formula instead of the class lookup, and every column after it should populate normally.
  5. If the resulting premium looks wrong, the first thing to check is whether PP_SpecificGroupIRate was filled in correctly — this workbook cannot detect a wrong hand-entered rate the way it might catch a bad table lookup.
