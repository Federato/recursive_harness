Correction to Step 2's “safe reading” — it was too loose. Step 2 said “ISO only fields are safe to omit, because we already rate without them.” That is only true when the rater's value is the neutral one. Our 44 payloads never sent VacantBuilding or SubStdConditionB because those test cases did not use them — not because the fields do not matter. The rater's own sample data has Vacancy = Yes and Sub Standard Condition – Wiring = Yes, and omitting either would price the risk wrong. Corrected rule: the export sheet carries every field the rater can source, whatever its evidence class. Evidence class decides what we default, not what we send. This is why the export sheet is ~90 columns and not the 74 Step 2 implied.

Resolved 2026-09-22 — FullBldgValue settled

Asked whether the scratchpad already computes this. It computes something adjacent, not this — and checking settled the question the other way.

What is actually there: CoreScratchpad!B138 is TOTAL LIMIT, and for the first item it is 1,190,000 = 675,000 Building + 515,000 Contents. B215 is Total Special Class Limit. That is the figure behind the DeductibleFactor fix (C41 = C138) and it feeds the deductible lookup at B139/B140.

Why it is not FullBldgValue: it totals limits, not insurable value, and it feeds the deductible factor rather than coinsurance. ISO's own Alabama sample keeps the two deliberately apart — Limit: 500000 against FullBldgValue: 550000, a building insured to 500k but worth 550k. Summing Building + Contents limits produces neither number.

The finding that settles it: across all 127 inputs the rater has Building Limit, Contents Limit, Business Income Limit and Special Class Building Limit — and no value field anywhere. The workbook already assumes limit = value, i.e. 100% insurance-to-value.

So the recommendation reverses. Option (a) was framed above as introducing an assumption. It does not — it reproduces one the rater already makes. Option (b) would make the payload more correct than the workbook, and in a three-way diff that manufactures a disagreement where ISO is right and Excel is wrong because of an input the generator invented. For a verification harness that is backwards: the payload must reproduce the rater's assumptions exactly, so every disagreement points at a real defect.

Decision: (a) for v1. FullBldgValue = Limit, FullSpecialClassValue = Special Class Building Limit — logged as a simplification, not silently adopted. Move to (b) whenever genuine coinsurance testing is wanted; that is a rater change first and a payload change second. Blast radius is probably small — the only observed consumer of FullBldgValue is ISO's “Full Value cannot be lower than the Limit” validation, which setting it equal satisfies. Not claiming zero rate effect; that is not established.

The multi-state split

One workbook run is several ISO requests. ISO carries state in SchemeKeys.ProductName, one state per request — there is no StateCode field to vary per location. The rater's sample data has four states live at once (FL, NY, AK, CA). So the CLI groups export rows by State, emits one payload per state, makes N calls, and reports N premiums plus a total. The Payload Export sheet needs no extra structure for this — State is already a LOCATION column and Python does the grouping.

How to build it — Step 4, in order

  1. Add two sheets to CFRater1.01.xlsb: Payload Export and Defaults. Hide both. Nothing else in the workbook changes.
  2. Build Defaults first — it is 12 rows of Field / Value, copied straight from the table above. Ten minutes, and it unblocks testing the reader before the big sheet exists.
  3. Lay out the nine blocks on Payload Export, top to bottom, in the order given here. Each block gets a row with the block name in column A, then a header row of ISO field names, then the data rows. Leave one blank row between blocks — that is how Python finds the boundaries.
  4. Fill each cell with a formula, never a typed value — ='Location Inputs'!C26 and so on. The point of this sheet is that it stays live. A typed value silently goes stale.
  5. Apply the seven format conversions from Step 1 as you go, in the formula itself: Coinsurance → =TEXT('Location Inputs'!C68*100,"0")&"%"; ZipCode → =TEXT('Location Inputs'!C13,"00000"). The other five are noted in the inventory.
  6. Transpose as you go. The input tabs run one column per item; the export sheet runs one row per item. Block 2's row for location 1 reads column C, row for location 2 reads column D, and so on.
  7. Build the RECORDS block last, with two Elected cells per Special Class exclusion even though both point at the same input today.
  8. Tell me when it is in and I will run Step 5 against it — the reader fails loudly on anything missing, so an incomplete sheet gives a precise error, not a wrong premium.
