Configuring Basic Group II's BGIIDeductibleByLocationFactor & DeductibleFactorBasicGroupII

What's genuinely new here, on top of what BldgBGIRating already built for Basic Group I: a second, independent deductible-by-location factor kept in its own field, and an outer branch that can swap the deductible-factor lookup key from the plain Deductible to a distinct WindstormOrHailDeductible.

Corrected 2026-09-08: the underlying DeductibleFactor table is not shared with Basic Group I the way this walkthrough originally assumed. The table has a fourth key column, CauseOfLossDeductible — BGI keys on "Other Cause Of Loss", BGII keys on "Basic Group II". Identical only at CW; every state that files its own table files genuinely different values for the two groups. This walkthrough now points at the correct, separately-built table (BGII_DeductibleFactor.xlsx), not BGI's AW:BB range.

STEP 2 / 7

BGIIDeductibleByLocationFactor — its own field, not Building's shared one

Basic Group I reuses one shared DeductibleByLocationFactor. Basic Group II keeps a separate copy, because the wind/hail deductible can diverge from the all-other-perils one on the same building.

Gate + lookup
' cell C46
=IF(AND(C45=0, C44<>"", C44<>"Not Applicable"),
   ' same DeductibleByLocationFactor table Basic Group I already built — flat 0.995, Yes/No only
   XLOOKUP("Yes", DeductByLocEndorsement_Col, DeductByLocFactor_Col),
   1.0)

Per CauseOfLoss_Building_RatingAlgorithms.md §Step 9: this factor only resolves to something other than 1.0 when wind/hail coverage isn't excluded (WindstormHailIndicator = 0) and a wind/hail-by-location record exists with a real value. It's the exact same underlying DeductibleByLocationFactor concept and table Basic Group I uses (flat 0.995 when the CP 03 29 endorsement applies, 1.0 otherwise) — Group II just stores the result in its own field because the gate condition differs from Group I's.

STEP 3 / 7

Which deductible actually drives the factor?

The one genuinely new decision Basic Group II adds to the deductible-factor step.

The branch, as Excel
' cell C47 -- which value keys the lookup in Step 5
=IF(OR(C44="", C44="Not Applicable", C44=C40),
   C40,   ' no distinct wind/hail deductible -- use the plain Deductible, same as Basic Group I
   C44)   ' a real, different wind/hail deductible is scheduled -- use it instead
⚠Note the third condition: C44 = C40. Even if WindstormOrHailDeductible is filled in, if it happens to equal the plain Deductible, the source rule still treats it as "no separate deductible" and falls through to the ordinary branch. Don't gate only on blank/Not-Applicable.
STEP 4 / 7

Build the BGII-specific Deductible Factor table

Same table name as Basic Group I's, genuinely different data — corrected 2026-09-08.

DeductibleFactor has a fourth key column, CauseOfLossDeductible, filed with three distinct values side by side: Basic Group I, Basic Group II, Other Cause Of Loss. Basic Group I's own rule keys on "Other Cause Of Loss" (not, confusingly, "Basic Group I"); Basic Group II's rule (SetDeductibleFactorBasicGroupII) keys on "Basic Group II" instead. At CW these two slices are byte-identical — zero differences across all 80 rows — which is what made the original "just reuse BGI's AW:BB table" plan look safe. It isn't: every state that files its own DeductibleFactor table files genuinely different values for the two groups (130+ differing rows per state, not a handful).

⚠Do not point this form's lookup at BGI's existing AW:BB range. Build a separate table, filtered to CauseOfLossDeductible="Basic Group II", all 46 non-PR states pulled from their own correct edition. Full data already pulled: BGII_DeductibleFactor.xlsx (40 states share BGI's 154-row shape with different values; FL/NV/TX/UT coarser; CA/NY fall back to CW). The one genuine exception is the flat Deductible="250" branch, which keys on the manual's group name ("Basic") rather than the form — that one sub-table really is shared.
STEP 5 / 7

DeductibleFactorBasicGroupII — same lookup shape, BGII's own table

Same row-offset/INDEX pattern as BGI's walkthrough, pointed at the BGII-specific table from Step 4 instead of BldgBGIRating, keyed on C47 from Step 3.

Row offset within the BGII deductible table (placeholder columns AW:BB on BldgBGIIRating — a separate block from BGI's own AW:BB on BldgBGIRating)
=SUMPRODUCT(
  (BldgBGIIRating!$AW$2:$AW$6669=$C$2)*
  (BldgBGIIRating!$AX$2:$AX$6669=$C$47)*
  (BldgBGIIRating!$AY$2:$AY$6669<$C$41)*
  (BldgBGIIRating!$AZ$2:$AZ$6669>=$C$41)*
  (ROW(BldgBGIIRating!$AW$2:$AW$6669)-ROW(BldgBGIIRating!$AW$2)+1))
Resolved factor
=IF(C47="250", Deductible250Factor_Lookup,  ' shared with BGI, keyed "Basic"
   IF(C47="Not Applicable", 1,
      INDEX(BldgBGIIRating!$AZ:$AZ, <actual-row cell>)))  ' BGII's own table, not BGI's

The 250-flat-deductible and Not-Applicable branches genuinely are shared with Basic Group I — same Deductible250Factor sheet, keyed on the manual's group name ("Basic"), not the form. The main step-function branch is not shared — it now points at BldgBGIIRating's own table (BGII_DeductibleFactor.xlsx's data, filtered to CauseOfLossDeductible="Basic Group II"), not BGI's BldgBGIRating!AW:BB. The key logic (C40 vs C44 per Step 3) is unchanged.

What this walkthrough doesn't cover

  1. Confirm real column addresses on BldgBGIIRating before building — C44–C47 are placeholders continuing the numbering pattern, not verified against a live tab.
  2. MultiResidentialPropSpecialCreditFactor isn't re-derived here — wire Calc_Building_BGII's FinalRate to the same Heat/Control lookups Excel_Rater_MultiResCredit_Walkthrough.html already built for Basic Group I. One set of tables, read by four forms' Building chains.
  3. The blanket branch and its truncation quirk (Truncate(BlktLimit/100) vs. Basic Group I's plain division) aren't built here — flagged in Excel_Rater_Wireframes.html's Basic Group II flow diagram, not yet designed into a tab.
  4. Percentage wind/hail deductibles (1%/2%/5%) aren't built here. When WindstormOrHailDeductible is a percentage rather than a dollar amount, it's resolved through a wholly separate table (WindstormOrHailDeductibleFactor), gated on WindstormHailIndicator=1, not through this walkthrough's DeductibleFactor table at all. If that indicator isn't set correctly when a percentage is chosen, the source rule silently zeroes the factor. This walkthrough only covers the dollar-amount path.
