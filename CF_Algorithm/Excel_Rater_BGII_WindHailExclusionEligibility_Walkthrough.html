Configuring wind/hail exclusion state eligibility for COLAdj

Eight states — AR, DC, FL, KS, NY, PR, RI, TX — file zero rows for both LowestBasicGroupIIRate and WindstormOrHailExclFactor. The wind/hail-excluded branch of COLAdj has nothing to compute with in those states. This walkthrough adds the one thing missing from the plain three-branch COLAdj already documented: a state-eligibility gate, so the UI stops a user from configuring an exclusion the data can't actually price, instead of silently producing a broken or null rate.

Per this project's standing decision, PR is out of scope — it's included below only because it's part of the same 8-state filing pattern in the ERC data; nothing here should be built or tested for PR specifically.

⚠ The regulatory "why" behind these 8 states is inferred, not manual-confirmed. The correlation (both tables empty, together, in exactly these states) is solid structural evidence; the general belief that coastal/wind-pool states restrict excluding wind/hail coverage is background insurance knowledge, not sourced from this project's circular corpus for these specific 8 states. Treat the mechanism below as confirmed, the regulatory reason as plausible but unverified.

STEP 2 / 5

The eligibility gate

One test, checked before the exclusion is ever allowed to apply.

Gate, as Excel (helper cell)
' cell BldgBGIIRating!C60 -- TRUE means this state CAN'T exclude wind/hail
=ISNUMBER(MATCH($C$2, WindHailExclIneligibleStates, 0))

$C$2 is the same State cell every other walkthrough on this tab already reads. This one cell now needs to gate two separate things downstream: whether the exclusion checkbox/dropdown is even usable (Step 3), and which branch COLAdj actually takes (Step 4) — both read this same cell so they can never disagree with each other.

STEP 3 / 5

The cheapest place to catch this is at data entry, not three formulas downstream.

Not available in TX — ISO files no wind/hail-exclusion rate data for this state. Leave unchecked.

Implementation: data-validation on the exclusion input cell, formula-driven off Step 2's gate — something like =IF($C$60,"No",IF(...normal Yes/No list...)) restricting the list to a single forced value when the gate is TRUE, plus conditional formatting (grey fill, locked cell, or a comment) so the restriction is visible, not just silently enforced. The warning message cell reads the same $C$60 gate.

STEP 4 / 5

Wire into COLAdj — the gate becomes a third condition

Same three branches as before, with one guard added to the middle one.

Before (plain three-branch COLAdj, already documented)
COLAdj =
    0.0                                              if fire-only cause of loss
    elif wind/hail exclusion NOT scheduled:
        Rate × StdPropPolGroupIIFactor
    else:
        LowestBaseRate × LCM × RoofSurfacingACVFactor × RoofSurfacingCosmeticExclFactor
          × WindstormOrHailExclFactor × StdPropPolGroupIIFactor
After (state-gated — the exclusion branch can only ever be reached in an eligible state)
COLAdj =
    0.0                                              if fire-only cause of loss
    elif wind/hail exclusion NOT scheduled OR C60 (state ineligible):
        Rate × StdPropPolGroupIIFactor
    else:
        LowestBaseRate × LCM × RoofSurfacingACVFactor × RoofSurfacingCosmeticExclFactor
          × WindstormOrHailExclFactor × StdPropPolGroupIIFactor
✓Because Step 3 already prevents the exclusion input from being set to "Yes" in an ineligible state, this OR C60 guard should never actually change the outcome in normal use — it's a second, independent line of defense in the calc itself, so a formula that reads the exclusion flag directly (bypassing the input-side restriction, e.g. a copy-pasted value or a future tab that doesn't go through the same data validation) still can't reach a branch with unresolvable data.
