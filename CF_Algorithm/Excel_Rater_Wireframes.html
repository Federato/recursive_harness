CF_Algorithm · Excel Rater Wireframes

What the Commercial Property rater looks like before anyone builds it

Sixteen mock spreadsheet tabs — Policy, Locations & Buildings, Rate Tables, Building and Contents calculation tabs for all four cause-of-loss forms, four more Business Income calculation tabs, and Premium Summary — laid out the way they'd actually sit in Excel, with the reasoning behind each one written in plain language underneath.

After each Building/Contents form's pair of calculation tabs sits a diagram, not a spreadsheet: what feeds the loss cost, what each stage produces, and the full rating formula with every if/then branch spelled out — the same walkthrough as each form's own build guide, drawn instead of written. Business Income's four tabs are short enough that the formula bar and instructions carry that same walkthrough directly, without a separate diagram.

These are pictures of a workbook, not a workbook. No cell here is live; every value shown is a plausible example chosen to make the layout readable. The real formulas are written out in Excel_Rater_BasicGroupI.md, Excel_Rater_BasicGroupII.md, Excel_Rater_Broad.md, Excel_Rater_Special.md, and the Excel_Rater_BusinessIncome_*.md set.

Everything on this row is a value you supply or schedule-rate yourself — none of it comes from an ISO rate table. That's the whole point of giving it its own tab: it's the short list of numbers that get read from every other tab, so there's exactly one place to change them.

  • State and EffectiveDate decide which edition of every rate table downstream applies to this policy.
  • LossCostMultiplier is the one ISO-adjacent number that lives here rather than on a rate table — it's filed per state and line of business, not looked up per building.
  • IRPMFactor, PackageModFactor, and MultiPremiumAndDispersionCreditFactor are all schedule-rating inputs — an underwriter's judgment, not a lookup. Every premium formula on the Premium_Summary tab multiplies by these three.

Shared / physical Building-only Contents-only

This is the widest tab in the workbook, and it's wide on purpose: Building and Contents rate the same physical building differently enough that each needs its own set of columns, even though ClassCode, ConstructionCode, Territory, and ProtectionClass only need to be entered once per building.

In the real workbook this tab runs about twenty columns wide — the mockup above shows a representative slice of each of the three blocks (shared, Building, Contents) rather than all of them, so the grouping reads clearly.

  • ClassCode means two slightly different things depending which coverage reads it — Building's rules call the same value ClassCodeToUse, Contents' call it BldgClassCode — but it's one column here, entered once.
  • PP_Group (A / B / C / YARD) has no Building equivalent at all — it's an occupancy grouping unique to how Contents looks up its base rate.
  • Bldg_CovType and PP_CovForm look like the same idea but drive different downstream branches — Building's premium formula branches on coverage type, Contents' on coverage form. Keeping them as separate columns, rather than one shared "coverage" field, avoids a mismatch neither rule file actually makes.
  • Basic Group II adds five more columns not shown above (kept off this mockup to keep it legible): NumStories, OpenSides, BasicGroupIIRatingTerr, WindstormOrHailExclusion, and a ConstructionSymbol column that's computed, not entered — resolved once here so both Basic Group II calc tabs can read the same value instead of each re-deriving it.

Every table here is pasted in once, in the same shape ISO filed it — a state-or-countrywide key column, then whatever keys that specific table needs, then the rate or factor. The calc tabs look values up here; nothing on this tab is computed.

The two-pass lookup every table uses is the same idea repeated: try the state's own row first, and only fall back to the CW row if the state hasn't filed one. In Excel that's IFERROR(XLOOKUP(state combo, …), XLOOKUP(CW combo, …)) — one formula pattern, reused down the whole tab.

!

Known gap, not a bug: BasicGroupIRate's countrywide rows are confirmed empty in the actual ISO package this project traced — zero data rows filed at the CW level, for both Building and Personal Property. Row 5 above shows what that looks like in the workbook: a visible red flag, not a silent blank or a zero. Any state without its own filed row will hit this — build the lookup so the gap is loud.

Basic Group II adds two more tables to this tab, and both are in worse shape: BasicGroupIIRate and LowestBasicGroupIIRate are each confirmed header-only at the countrywide level, for both Building and Contents — meaning Basic Group II's loss cost cannot resolve at all, under any symbol/territory combination, without a state filing. See the Basic Group II calc tabs below for what that looks like once it reaches a formula.

Read left to right and each column is one rating step, in the exact order ISO's own rule file runs them — base rate, then rate, then a cause-of-loss adjustment, then coinsurance and limit-of-insurance factors, then deductible, landing on FinalRate.

BLDG-B's row shows the empty-CW-table gap arriving downstream: because BaseRate can't resolve for a state that hasn't filed its own row, every column after it that depends on it goes blank too, all the way to FinalRate. That's deliberate — a wrong-but-present number would be worse than a visible break in the chain.

  • Rate (step 2) is the only column with an addition inside it — base rate times the loss-cost multiplier, plus a substandard-condition addend and a vacant-building addend, before the multipliers apply.
  • CoinsuranceFactor (step 4) is sometimes left exactly as-is rather than recalculated — for class code 1150 or a Functional Valuation policy, the rule skips this step entirely rather than overwriting it with 1.0.

Same nine-step shape as the Building tab, but don't assume the columns line up one-for-one — three of ISO's real differences are visible right in this layout, not just in the numbers.

  • VaultFactor (step 2) has no column on the Building tab at all — a 0.50 credit for contents kept in a fire-rated vault, a concept that only makes sense for contents in the first place. BLDG-B's row shows it applied.
  • Rate (step 4) is missing two things the Building tab's equivalent step has: no vacant-building addend, and no roof-surfacing factor. Contents don't have a roof, and vacancy for contents is rated by a separate endorsement, not folded in here.
  • FinalRate has no multi-residential credit multiplier — that Building-only discount doesn't exist anywhere in ISO's Personal Property rules.
★

Column 9, DeductFactor, is a documented deviation, not a guess. In ISO's own rule files, this value is copied down from an unrelated ancestor record rather than computed inside the Personal Property ruleset — an organizational quirk of how ISO split its files, not a different formula. This workbook builds it as the same local lookup used on the Building tab, since the underlying table and logic are identical. If a real ISO test system ever disagrees with this workbook on a Contents deductible factor, this is the first cell to check.

Building — full formula

BaseRate = Lookup(BasicGroupIRate: ClassCode, ConstructionCode, "Not Applicable", "Building")
    if RatingType = "Class" and ClassCode <> "" and ConstructionCode <> 0
    else 0.0

Rate =
    if RatingType = "Class":
        ((BaseRate × LCM) + SubStdConditionRate + VacantBuildingRate)
          × TerrFactor × ProtClassFactor × RoofSurfacingACVFactor
    elif RatingType in ("Specific","Tentative"):
        SpecificGroupIRate × LCM × SprinklerLeakageNotExcludedFactor
    else: 1.0                                            (round to 3dp)

COLAdj = Round(Rate - SprinklerLeakageExclNonSprinkleredBldgRate, 3)
          × SprinklerLeakageExclSprinkleredFactor × VandalismExclFactor × StdPropPolGroupIFactor
(...BldgRate = Round(rate × LCM, 3) -- at LCM=1.0 this rounds the filed 0.0006 up to 0.001, a ~67% jump from crossing the 3dp boundary)

CoinsuranceFactor =
    <left unchanged>   if ClassCode = "1150" or ValuationType = "Functional Valuation"
    else <standard 80/90/100% lookup>

AdjustedRate = COLAdj × CoinsuranceFactor × LOIFactor

DeductibleFactor =
    Lookup(Deductible250Factor)                        if Deductible = "250"
    else Lookup(DeductibleFactor: Deductible, TotAmtInsurance, "Other Cause Of Loss")
    (★ corrected: TotAmtInsurance = Bldg limit + every Contents item's limit at the location + Special Class Risk -- NOT Bldg limit alone. Live rater still uses Bldg-only; backlogged until Contents is built.)

FinalRate = AdjustedRate × DeductibleByLocationFactor × DeductibleFactor × MultiResidentialPropSpecialCreditFactor

Bldg_Premium =
    if Bldg_CovType in ("Building","Builders Risk","Improvements and Betterments","Condominium Association")
       and Bldg_IncludedInBlkt = "No":
        Round(IRPM × MultiPremiumDispersion × PackageMod × FinalRate × (Limit/100), 0)
          × CyberExclFactorBGI × CyberExclCOLExcptnsFactorBGI
    elif Bldg_CovType = "Legal Liability": [not built this pass]
    elif Bldg_IncludedInBlkt = "Yes":     [blanket — not built this pass]
    else: 0.0

Contents — full formula

BaseRate =
    if RatingType = "Class" and ClassCode <> "1150":
        if PP_Group = "YARD":
            Lookup(constCode = 1 or 3 by YardPropertyIndicator, group="YARD", covType="PersProp")
        elif ConstructionCode <> 0 and PP_Group <> "":
            Lookup(ClassCode, ConstructionCode, PP_Group, "PersProp")
        else: 0.0
    else: 0.0

FireSafeVaultFactor = 0.50 if PP_FireSafeVault = "Y" else 1.0   (0.0 unless RatingType = "Class")

Rate = ((BaseRate × LCM) + SubStdConditionRate) × FireSafeVaultFactor × ProtClassFactor × TerrFactor
       (no vacancy addend, no roof factor at any branch)

COLAdj =
    0.0   if PP_ValuablePapers = "Y"
    else Round(Rate - SprinklerLeakageExclNonSprinkleredRate, 3)
           × SprinklerLeakageExclSprinkleredFactor × VandalismExclFactor × StdPropPolGroupIFactor
    (Contents' own datadef group names its LCM-scaled value "Rate" with no suffix -- different from Building's "...BldgRate" above)

CoinsuranceFactor =
    <forced to the 100% lookup value>
        if (SpecialCoinsuranceProvisions or ValueReportingForm record exists
             or Coinsurance in ("Daily","Weekly","Monthly","Quarterly","Policy Year Reporting"))
           and ValuationType <> "Functional Valuation"
    else <standard lookup>

LOIFactor =
    <blanket copy>   if PP_IncludedInBlkt = "Yes" and BlktIDNum > 0
    elif PP_CovForm not in ("Legal Liability Coverage Form","Tobacco Sales Warehouse Coverage Form"):
        Lookup(BasicGroupILOIFactorPersProp: PP_Limit)
    else: 1.0

AdjustedRate = LOIFactor × COLAdj × CoinsuranceFactor

DeductibleFactor = <same local Choose Building uses>  (★ documented deviation — ISO copies this from an ancestor record)

FinalRate = AdjustedRate × DeductibleByLocationFactor × DeductibleFactor  (no multi-res multiplier, any branch)

PP_Premium =
    if PP_CovForm not in ("Legal Liability Coverage Form","Tobacco Sales Warehouse Coverage Form",
                           "Class Rated Building Only, No Personal Property Coverage")
       and PP_IncludedInBlkt = "No":
        Round(IRPM × MultiPremiumDispersion × PackageMod × FinalRate × (PP_Limit/100), 0)
          × CyberExclFactorBGI × CyberExclCOLExcptnsFactorBGI
    elif PP_CovForm = "Legal Liability Coverage Form": [not built this pass]
    elif PP_IncludedInBlkt = "Yes":     [blanket — not built this pass]

!

DeductibleFactor here is the same 7-state-shape table Basic Group I uses (47 states, 2-pass State-then-CW XLOOKUP, worked example in BldgBGIRating's Deductible Factor walkthrough) — the only thing Basic Group II adds is the outer branch that swaps the lookup key from Deductible to Bldg_WindstormOrHailDeductible when a distinct wind/hail deductible is scheduled. Build the table once, reuse it for both forms; don't re-derive it per form.

!

MultiResidentialPropSpecialCreditFactor is the exact same mechanism as Basic Group I's — same gate (12 apartment class codes, MultipleResidentialPropSpecialCredit <> "No"), same Heat × Control combine, and the same state variation: CT discounts the Control factor to 0.50 (vs. CW's 0.70); MA/ME disable the credit entirely via a restricted input domain, not a rate override. Full mechanism, all three tables, and a live worked walkthrough: Excel_Rater_MultiResCredit_Walkthrough.html and BGI_MultiResidentialPropSpecialCredit.xlsx. Wire the same two lookups into Calc_Building_BGII's own FinalRate — don't rebuild the tables a second time.

One premium column pair per cause-of-loss form built so far — every pair shares the exact same shape, round the rate times the limit times three schedule-rating factors to whole dollars, then multiply by two cyber-exclusion factors — because that's what ISO's own rule files do for every form's scheduled, non-blanket, non-Legal-Liability branch.

BLDG-A and BLDG-B both read $0 across every Basic Group II column, and for a different reason than the earlier Basic Group I gap: it isn't that one building's rate failed to resolve — no building's Basic Group II rate can resolve yet, because both BasicGroupIIRate and LowestBasicGroupIIRate are empty at the countrywide level for every symbol/territory combination. BLDG-B's Basic Group I Building premium is also flagged, for the original, narrower reason — its own class/construction combination has no filed row.

The Broad columns read a plain, unflagged $0 — not a warning — because neither building's policy selected Broad as its cause of loss in this example; the gate on Bldg_CovType/PP_CovForm plus CauseOfLoss = "Broad" simply doesn't fire. That's the distinction the flag exists to protect: a legitimately-inapplicable form and a broken lookup both produce 0, but only one of them should carry a warning icon.

Special tells the third version of this same story. BLDG-B ★ is a Builders Risk building (class 1150) — its Bldg_Special_Premium actually resolves, $15, because SpecialBuildersRiskRate is one of the few tables in this form that has real CW data. Its PP_Special_Premium is flagged anyway, because Contents' Special depends on three different tables (SpecialPrsnlPropRate, SpecialPrsnlPropTheftExclusionFactor, PrsnlPropTerrMultiplier) that are all empty — the same building, same form, one coverage resolves and the other can't, for entirely independent reasons.

The four BI_* columns are one coverage, not two — Business Income doesn't split into a Building/Contents pair the way every other coverage in this workbook does, so it earns four columns instead of eight. BI_BGI and BI_BGII both read $0 ⚠ for every building — not because either building's data is unusual, but because these two forms doubly (BGII: triply) depend on countrywide tables already confirmed empty, on top of a Business-Income-specific adjustment table that's also empty. BI_Broad reads a plain unflagged $0, same "not selected" story as the Building/Contents Broad columns. BI_Special is the one Business Income column that resolves for BLDG-B ★ — $9 — because, like Building's own Special, its Builders Risk table has real data; unlike Contents' Special, Business Income's Special has no data gap of its own at all.

!

Zero and "couldn't calculate" must never look the same on this tab. A legitimately zero premium (say, a coverage type this pass doesn't rate yet, or — as with Broad here — a cause of loss the policy didn't select) and a broken lookup upstream both produce the number 0 unless the flag column is built in — treat the flag as load-bearing, not decorative. That matters more, not less, now that three coverages and four-to-eight forms apiece can all land premium columns on the same row.
