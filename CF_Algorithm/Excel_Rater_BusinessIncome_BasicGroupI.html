1. The one thing that makes this form different

Business Income's Basic Group I does not compute its own base rate. It reads Calc_Building_BGI.BaseRate — the same value Building's own Basic Group I already computed for the same structure. Rate the Building first; this tab is arithmetically downstream of it, not a parallel computation.

4. The algorithm

1BGIBaseRateAdjustmentFactor

Lookup(BaseRateAdjustmentFactor: State|CW, "Basic Group I")

2Rate class-rated path

if (BI_MaxPeriod = "Y" or BI_MonthlyLimitOfIndemnity <> "Not Applicable" or BI_CovType = "Extra Expense Only") and BI_BldgIncludedInOperationalUnit = "Y": HighestBusnIncomeBasicGroupIBaseRate × BGIBaseRateAdjustmentFactor -- blanket/multi-unit, out of scope elif RatingType = "Class": ((Calc_Building_BGI.BaseRate × LCM) + SubStdConditionRate + VacantBuildingRate) × BasicGroupIRatingTerrFactor × ProtectionClassFactor × BGIBaseRateAdjustmentFactor elif RatingType in ("Specific", "Tentative"): SpecificGroupIRate × LCM × SprinklerLeakageNotExcludedFactor × BGIBaseRateAdjustmentFactor -- does NOT read Calc_Building_BGI.BaseRate at all in this branch -- round to 3dp

Same addends, same territory/protection-class factors Building's own class-rated formula uses — this is Building's Basic Group I rate formula with one extra multiplier (BGIBaseRateAdjustmentFactor) tacked on, sourced from columns Building's own tab already reads.

3COLAdj

ROUND(Rate − SprinklerLeakageExclNonSprinkleredRate, 3) × SprinklerLeakageExclSprinkleredFactor × VandalismExclFactor × BuildersRiskFactor -- round to 3dp; always recomputes, no null-guard (unlike Building's version)

4Factor shared across Basic Group I & II only

if BI_MaxPeriod = "Y": MaxPeriodOfIndemnityFactor elif BI_MonthlyLimitOfIndemnity <> "Not Applicable": MonthlyLimitOfIndemnityFactor elif BI_CovType = "Extra Expense Only": ExtraExpenseFactor else: Lookup(BusnIncomeFactor: CoinsuranceToUse, BI_CovType, BI_TypeOfRisk)

Business Income's functional replacement for Building's flat CoinsuranceFactor — folds coinsurance percentage, type-of-risk, coverage type, and two special-case periods into one number. Confirmed by grepping Broad's and Special's rule files for CoinsuranceToUse/ TypeOfRiskFactor/BusnIncomeFactor: no matches in either — Broad and Special never multiply by this factor at all, it's Basic Group I/II only.

5FinalRate

COLAdj × Factor -- that's the entire final-rate step. No coinsurance factor, no LOI factor, -- no deductible factor of any kind — stage 4 above does the entire job -- those three separate Building stages do, for this and one other form.

5. Premium

if BI_IncludedInBlkt = "No": ROUND(ROUND(IRPMFactor × PackageModFactor × FinalRate × (BI_Limit / 100), 0), 0) × CyberIncidentExclusionFactorBGI × CyberIncidentExclusionCOLExcptnsFactorBusnIncomeBGIToUse elif BI_IncludedInBlkt = "Yes" and BlktTotalFullValueAmount > 0: -- blanket branch, out of scope — needs BlktBasicGroupIAvgRate, -- FullBusnIncomeValue, BlktTotalFullValueAmount else: 0.0

No gate on coverage type or cause of loss the way Building's own Basic Group I premium has — this branch always fires as long as the coverage isn't blanketed, since ISO's own SetCoverageOnPolicyIndicator is a hardcoded 1 for Business Income. MultiPremiumAndDispersionCreditFactor is populated during shared prep but never actually multiplied into this premium formula — don't add it by assumption.

7. Deliberately out of scope for the first build

  • The blanket/max-period/multi-unit base-rate branch — needs HighestBusnIncomeBasicGroupIBaseRate, a multi-unit aggregate not traced yet.
  • The blanket premium branch — needs BlktBasicGroupIAvgRate, FullBusnIncomeValue, BlktTotalFullValueAmount.
  • CoinsuranceToUse's real blanket-rating-table scan — enter the resolved value directly as a simplification for now.
  • The "Combined…" TypeOfRisk blended-factor branch — flagged unsupported.
  • Specific/Tentative rating is NOT out of scope — see the algorithm's step 2 above, same RatingType branch as Building's own Basic Group I, with the extra BGIBaseRateAdjustmentFactor multiplier tacked on. Note it does not read Calc_Building_BGI.BaseRate — it substitutes SpecificGroupIRate directly, same open question as Building's own version (no Set/Lookup rule populates it anywhere — likely a user- or schedule-entered value, unconfirmed). Give this its own BI_SpecificGroupIRate input column, separate from Building's and Contents' — no reason to assume all three share a value for the same building.
