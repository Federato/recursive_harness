Streamlining the CF rater — what the harness build teaches

2026-09-22. Eight suggestions, each one traced to a specific thing the Recursive Harness build learned the hard way. These are proposals, not decisions — nothing has been written to CFRater1.01.xlsb. Ordered cheapest-first within each tier; the priority table at the end ranks them by payoff per hour.

The through-line. The harness's nine-point gate exists because every one of its points was, at some stage, a bug that a clean-looking result hid. The rater produces numbers the same way the harness did before the gate — correctly, most of the time, with no way to tell the difference between a right answer and a wrong one that looks right. Almost everything below is about making that distinction visible inside the workbook, rather than discoverable only by a person reading rule XML afterwards.

Tier 1 — cheap, high payoff

R-1 Name every input, and stop addressing by position ✓ DONE 2026-09-22

Implemented. 133 names added to CFRater1.02.xlsb (a copy — 1.01 is byte-identical to before), 0 failed, and 133 of 133 verified to resolve to the correct cell by two independent paths. Item tabs got a name per input row ($C:$L / $C:$E), so the INDEX(range,1,ordinal) pattern survives rows moving. Full record, including the reusable COM write protocol: CF_R1_Implementation_Record.md.
Why: Entry 33 — rows and columns moved repeatedly inside a single working session, and every cell reference given that day was wrong until caught by hand. This is the single largest source of friction in the whole project, and it silently taxes every other item on this page.

Convert each input block to an Excel Table (Ctrl+T) and give every input row a name. Formulas then read structurally instead of positionally:

 Today — positionalAfter — named
 =INDEX('Location Inputs'!$C$26:$L$26,1,$A20)=INDEX(IN_Bldg_ClassCode,1,$A20)
 ='Location Inputs'!C68=IN_Bldg_Coinsurance
 =CoreScratchpad!C138=CALC_TotalLimit
 breaks when a row is insertedsurvives inserts, moves, re-ordering

Do this first. It makes the Payload Export sheet trivial, it makes every future doc durable, and it retires the "re-read the workbook before trusting any cell reference" caveat that currently opens every handoff.

R-3 Guard and provenance columns on every calc row ✓ DONE 2026-09-22

Implemented. 434 rows annotated across the four CALC - sheets with M = Source (parsed from each row's real formula) and N = Check (174 live zero-checks). Premiums unchanged — the only change in this series that is additive by construction. The tuning was the work: the first run flagged 46, the tuned version flags 3. Noise came from block titles holding a typed 1, and from zeros that are legitimate — additive rates, unelected forms, branch-only values. Only multiplicative terms are zero-checked, since only those take the chain to zero. All 3 surviving flags were investigated and are benign — including one that looked exactly like the =1 defects R-4 and M-1 found, but turned out correct: ISO files the multi-residential credit for Building only, so Contents' hard-coded 1 is right. A hard-coded 1 sometimes means “does not apply here” — the Source column's job is to make that visible for a human, not to declare it wrong. Full record: CF_R3_Implementation_Record.md.
Why: the two most expensive lessons at once. Gate point 4 — every 0 tested against its consuming branch, because eight known inputs price a chain at zero silently. Gate point 1 — every intermediate traced to a named rule and table row. Today a factor cell holds a number and nothing else.

Three extra columns beside each factor. Cheap, and they turn the calc tabs from an answer into an explanation:

Row 15 is the whole point. That is the real, documented Joisted Masonry case: an input that is spelled correctly, is semantically right, is the name printed on the rate table — and misses the domain lookup, pricing the chain at zero. Today the workbook shows 0.000 and a plausible final premium. The Check column costs one IF per row and turns a silent mispricing into something you cannot miss.

Columns C and D can be text written once per step — they do not need to be computed. Their value is that the next person diagnosing a wrong number reads the key instead of reconstructing it.

R-4 One policy-level factor block, referenced everywhere ✓ DONE 2026-09-22

Implemented — but the survey rewrote the job first. Two of the five factors named below were already correct and were left alone: LCM is a genuine per-state lookup, not a flat 1.0, and CyberExcl* already gates off 'Policy Inputs'!$F$3. Collapsing Cyber would have been a bug — its 0.997-vs-0.996 split between Broad and Special is filed data, and merging it would have reintroduced the premium defect fixed in BUILD-LOG Entry 28. The real problem was narrower and worse: IRPM, PackageMod and MultiPremiumDispersion were hard-coded 1.0 in 120 cells with no input anywhere — applying an IRPM meant editing 40 cells. 3 inputs added, 150 cells repointed, premiums unchanged at 1.0 and moving correctly at 0.9. The two-sided check caught a second defect: Business Income's cells held the formula =1 — a literal disguised as a formula — so BI was inert; 30 more cells fixed. Open finding (backlog M-1): Special Class and SCBI apply none of these three, though ISO files all of them. Full record: CF_R4_Implementation_Record.md.
Why: BUILD-LOG Entry 33 flagged this and it was never fixed — MultiPremiumAndDispersionCreditFactor and both Cyber exclusion factors are policy-level, endorsement-gated values, but every coverage tab carries its own independent flat 1.0. The harness separately confirmed MultiPremium is live on 12 of 20 premium files and genuinely absent on 8 — so the right value is not uniformly 1.0, and four tabs will need changing in four places the day that matters.

Tier 2 — structural, higher payoff

R-5 Split the exclusion inputs per datadef group ✓ DONE 2026-09-22

Implemented — and the scope below was understated by more than half. The backlog describes two filed records per exclusion; ISO files five, one per coverage group — 15 records driven by 6 inputs. 15 per-group inputs appended (IN - Location 96–104, IN - Special Class 49–54), each a formula pointing at its master so electing an exclusion still turns it on everywhere; type No over one cell to split a single coverage. 161 cells across 17 consumer rows rewired. R-6 Put the edition and state basis on the face ✓ DONE 2026-09-22

Implemented, and built differently from the sketch below. 19 source stamps (one per TBL - sheet), a new TBL - Editions (52 rows — 47 filed plus explicit NO FILING rows for HI/ID/LA/MS/WA), and OUT - Diagnostics §5 resolving each active location live. R-7 A diagnostics tab, including the message register ✓ DONE 2026-09-22

Implemented as OUT - Diagnostics, position 4, with four sections rather than the one drawn below. (1) a live COUNTIF roll-up of R-3's flags per sheet; (2) six live input traps — each one a documented defect, including Z-1's blank additional-insurable-interest option and T-1's short total, which was failing until today; (3) ADJUDICATED — the three R-3 flags with their verdicts, so they are not re-investigated every time someone opens the workbook; (4) standing assumptions. R-8 Row-per-item inputs, so the workbook can hold a real policy Structural ~2 days

Why: gate point 3, enumerate rather than sample — and a hard ceiling found this week. The input tabs run one column per item, which caps the workbook at 10 locations × 1 building × 1 occupancy class. ISO's own structure allows N of each, and harness chunk 4 proved ISO sums multiple occupancy classes per location. The workbook cannot express the shape it is meant to price.

One sequencing decision worth making before Step 4. R-8 (row-per-item) and the Payload Export sheet solve overlapping problems — the export sheet exists largely to transpose column-per-item into row-per-item. Build the export sheet now and R-8 later, and the transposition gets built, then thrown away. Do R-8 first and the export sheet shrinks to mostly direct references. Not a recommendation to delay Step 4 — it may well be worth having a working generator sooner. But it is a real choice, and it is cheaper to make now than after.

Remaining steps

  1. Pick a tier, or pick R-1 alone. R-1 pays for itself against anything else on the list and does not commit you to the rest.
  2. Decide the R-8 / Step 4 sequencing above — the only question here that gets more expensive with time.
  3. Each of these is a spec, not a build. Say which and it gets the same treatment the payload sheets got: exact rows, exact formulas, then you build it.
  4. Nothing gets written to CFRater1.01.xlsb by me at any point.
