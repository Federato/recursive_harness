2Why it's an interpreter

Say
  • ISO publishes its rating content as a program, not as a document — 20,673 rule files across 567 packages.
  • There are two ways to use that. Rewrite ISO's rules in our own code, in which case every ISO release means re-coding. Or read and execute ISO's files directly, in which case every ISO release is a file drop.
  • We do the second.
Do
  • Switch to the file explorer at ISO's folder
  • Open NJ to show the editions inside it
Say
  • 89,065 files, under a gigabyte. One folder per state, one folder per edition inside it.
  • Old editions are kept, which is how a backdated rating resolves to the version that was in force at the time.
Do
  • Open a rate table CSV in Excel
Say
  • ISO's tables are CSVs. They aren't copied into a database — the engine reads them where they sit.
  • So ISO updates need no code changes, and one engine covers every jurisdiction.
  • The cost is that every ISO instruction had to be specified before anything could run. There are 54 of them.
Say — carriers on older editions
  • Carriers don't all adopt every ERC edition. A carrier may be filed to use one from years ago.
  • The engine never assumes the newest edition. It selects the edition in force, and it pairs each state package with the countrywide edition that package declares — not the newest one.
  • So running a carrier on an older edition is configuration, not an engine change: pin the edition per carrier and per state, since a carrier can be current in one state and behind in another.
  • Not built yet. The mechanism it needs is already there, and already used for backdated ratings.

3The code that matters

Do
  • Switch to the editor
  • Open each of the five files in turn as you name it
Say
FileWhat it does
interp/nodes.pyISO's 54 instructions, one function each — if, and, or, equal, choose, and the rest
interp/interpreter.pyExecutes them. On an instruction it doesn't recognise, it stops rather than continuing
resolve/resolver.pyDecides which ISO package applies for a jurisdiction and date — state layered over countrywide
erc/tables.pyReads ISO's tables, typed from ISO's own definition files rather than inferred from the data
rating/kernel.pyEntry point. Submission in, rating out
  • About 5,000 lines in total.
  • No jurisdictional content is in the code. All of it is in ISO's files.

4How we test and improve it

Do
  • Open PROCESS_LOG.md at the standing criteria
Say
  • The build ran in six stages. Each stage had acceptance tests that had to pass before the next began. There are thirteen test suites.
  • The evidence rules were set before any code was written:
  • ISO's files are the only source of a value.
  • The manuals may confirm what something means. They may not supply anything the files lack.
  • Anything neither settles is escalated to a person.
  • Nothing is invented. If a value can't be sourced, the engine returns a referral instead of a number.
  • These are enforced in code, not by review — a value that can't name its ISO source can't be constructed.
Say — the recursive part
  • Rules were added during the build, from the build. When the same class of error recurred, it was written up as a standing rule with every instance listed underneath it.
  • 53 analysis steps preceded the engine code. 90 open items are tracked; resolved ones are marked, not deleted.
Do
  • Switch to the backlog
Say — current method and next steps
  • Every submission is rated by both our engine and ISO's live service, then compared field by field.
  • Until last week every comparison used one risk shape. Widening began on 14 August — 17 variants across 7 groups, and 31 of 31 comparable variants matched in Oklahoma and New York.
  • That widening found three defects, including one where our engine accepted a submission ISO rejects.
  • Next: keep widening the comparison population until it stops finding defects.
  • After that, carrier deviations — which layer on top of ISO's content the same way a state layers over countrywide. Not built.
