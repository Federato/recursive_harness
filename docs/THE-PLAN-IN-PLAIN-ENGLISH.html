1What we're building

A system that takes a General Liability submission and produces a premium, the way ISO says to.

ISO publishes the rules for pricing commercial insurance. They arrive two ways: as manuals written for people to read, and as data files written for machines. We hold both — around 87,000 files of data covering all 51 jurisdictions, and 1,122 manual documents.

The engine reads the data files and does what they say. For any risk, at any date, in any state, it should produce the same number ISO's own service would — and show its working, so anyone can see which file each number came from.

Where ISO declines to put a price on something, the engine must decline too, rather than guess. That turns out to be a large part of the job.

2Why it's hard

Not the arithmetic. The arithmetic is multiplication. The difficulty is that almost nothing means what its name suggests.

The rules change by date, and one date changes almost everything

The data files contain filings that haven't taken effect yet. Any count taken over "the latest version" describes the future, not today. On 1 April 2027, forty-three states change classification basis on the same morning and one rate table disappears with it. An engine that caches "the current rules" breaks that day; one that picks rules by effective date never notices.

Every state can rewrite any rule, and "empty" is a decision

A state can replace a national rule with nothing at all — and that means "we don't do this here", not "use the national one". New York does it 151 times. It can also replace a rule with a harmless-looking constant, which does the same thing while looking like ordinary code — New York does that 98 times.

A zero is usually not a number

Zeros in these files have eight distinct meanings. Sometimes zero is a price. More often it means "refer this to an underwriter", or "price this a different way", or "this class isn't eligible". Multiply by it without checking and you write a free policy on exactly the risks meant for human review.

Names lie, consistently

Rules are named for the calculation they perform, not the thing they calculate. One railroad rule is named for class 40014, tests class 40011, and writes to a field named after class 40006 — which is an unrelated classification. Two rulebooks in force today share the same 4,461 rule names with 345 different behaviours between them.

3The one rule everything follows

Adopted early, tested hard, and it has held.

The data files are the source. The manuals confirm and never source. Nothing is assumed. Anything unresolved comes to you rather than to a default.

Concretely: if the data files say a factor is 0.85, that's the factor. If the manual says something different, that's an escalation, not a correction. And if a calculation can only be found in the manual, the engine doesn't do it — it stops and asks.

This rule was refined once, deliberately, on 12 August. Asking a broker a question that can only ever stop a quote — never change a price — is now allowed even where ISO's data has no field for it, because declining to price takes nothing from the manual. The limit matters more than the permission: an input that could move a number still may not come from the manual.

The discipline has paid for itself repeatedly. Eighteen questions have been escalated; eight of them dissolved the moment somebody opened the file they were about.

5What we learned that changed the design

Each of these came out of a walkthrough, and each would have produced a wrong engine if assumed otherwise.

Coverages can't be priced independently

We assumed each coverage was self-contained. Three of them aren't. Cyber and Electronic Data read five values computed inside another coverage. Terrorism reads four coverages' finished premiums. So the order things are calculated in is part of the rules, not an implementation detail — and terrorism has to go last.

A state's rulebook is not a patch on the national one

It replaces named pieces wholesale. California is the only state on an older national rulebook, and 345 rules behave differently for it under identical names. An engine that merges the two layers, or takes the newest, is wrong for a whole state.

The same table is filed under different names in different states

New Jersey and Ohio split one rate table into fifteen and ten, one per territory. New York does the same and also splits the instruction that says how to price. Ask for a table by name and you find an empty one; follow the rule instead and you find the rates.

Validation messages are part of the pricing

Several bounds exist only inside rules whose entire job is to raise a warning. One calculation can produce a negative premium and the only thing preventing it is a message rule. Port the arithmetic without the warnings and the engine quotes negative numbers.

7What you decided

Thirteen decisions on 12 August. Three of them changed how the engine has to be built, not just what it prices.

The engine is built for one carrier, and set to match ISO's own service

The company's loss-cost multiplier is fixed at 1.0 so that engine output is directly comparable with ISO's rating service. Any difference is then a defect in our engine and never a difference in company filings — which makes every future comparison meaningful. It also means the engine refuses to start until it has been told its company parameters, rather than quietly defaulting.

"Refer to company" means stop, say what you need, and resume

Where ISO declines to price something, the engine now names the value it wants, an underwriter supplies it, and pricing continues. A referral is a pause, not a dead end.

That created two different kinds of company input — one set once when the engine is configured, one supplied per risk at the moment of referral — and the architecture carries both.

Which then invalidated a rule we'd already written

We had said a referral blocks anything multiplied by it, but not anything added to it. Terrorism is calculated by adding several premiums together and then multiplying — so under that rule it would have quietly priced on an incomplete total.

Because referrals now resume, the missing number is coming — so anything depending on it waits and is calculated once, properly. The rule is now about whether the answer is on its way, not about the arithmetic. The rest of the policy still prices: twenty classifications with one referral still quote the other nineteen.

One more, small and worth keeping: once something has gone to an underwriter, it stays gone. A recalculation can never quietly cancel it.

8How we'll know it's right

Better than we thought a week ago, because of something you spotted.

We had recorded that the project held one fully-priced example policy to check against. It holds 54, covering 50 states — they had been sitting in a folder, described in our own tracking register, and a claim measured in one place had been stated about everything.

What that changes: most completed coverages can be checked against ISO's own answers on day one, rather than only the two the single example exercises. California and New York — the two states we'd singled out as untestable — both have answer keys.

Two things still have none. Loss history for experience rating appears in no example, and the rounding tie-break — what happens at an exact halfway point — isn't stated anywhere in the data. Both need ISO's live service, and that is now worth connecting to earlier than planned rather than last.

Detailed testing strategy is deliberately deferred — it comes after the build shape is settled.

9What is not decided

The insurance content is specified. The software shape is not, and one question governs the rest.

DECIDED 12 August — run ISO's rules directly

Chosen on a measurement rather than a preference. ISO's instruction language turns out to be 58 kinds of instruction across 809,088 uses, and the twenty commonest cover 94%. Implementing that language once — roughly twenty instructions for a working version, 54 for a complete one — means every state, every coverage and every future ISO filing comes free. The alternative was hand-writing 4,461 rules per package plus 345 more for California alone, then repeating it every time ISO files.

The build is now specified in six signed-off stages — see docs/BUILD-STAGES.md. The original framing of the choice is kept below, because it is why the answer was not obvious.

The fork, as it stood before the decision

ISO's data files don't just hold rates — they hold the rules, about 4,500 per package, written as structured instructions a machine can follow. There are two ways to build against that, and the plan has never chosen.

Run them. Build something that executes ISO's instructions directly. Then California's 345 differences cost nothing, and so does every future filing — but we have to implement ISO's instruction language exactly, including the awkward parts.

Rewrite them. Hand-write each calculation in ordinary code, guided by the eleven walkthroughs. Far easier to read and debug — but California needs 345 hand-written differences, and every new ISO edition needs another pass.

This was the decision that unblocked writing code. It is now taken.

Three smaller gaps, all specification rather than judgement:

  • No defined submission format. We know the engine needs around 1,900 possible input fields and we have 517 real submissions to shape it from — but nobody has written down what a request looks like.
  • No defined audit trail format. Several decisions now depend on it — recording that terrorism was withheld rather than zero, and that a referral was raised and resolved.
  • Two coverages aren't walked through yet — capture handling and whole-policy assembly.
