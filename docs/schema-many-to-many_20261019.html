GL & Property schema: many-to-many relationships

Taken from ISO ERC data definitions: MasterGLCW.DataDef.xsd (GL CW 2027-04-01 V02) and MasterCFCW.DataDef.xsd (CF CW 2027-01-01 V01). Reviewed 2026-10-19.

In short

Think of ISO's data as a family tree: every record has exactly one parent (a building belongs to one site, a site to one policy). Real insurance doesn't work that neatly. One bank lends on many buildings, and one building can be in several shared limits. ISO squeezes these "many-to-many" links into the tree in five ways:

Bridge record a child line that links two things  ·  Number pointer a number that points to a record elsewhere  ·  Schedule text a name or address typed into an add-on  ·  Duplicate types the same add-on copied for each place it can attach  ·  Repeated columns / flags extra boxes on one line instead of extra lines

Is this every example? It covers every pattern in both schemas. Both files were scanned field by field for links between records. The 106 GL and 59 Property schedule tables, and the 63 Property add-ons copied across item types, repeat these patterns, so each pattern is shown once with its count rather than listing every table.

Each relationship

GLBridge record

1 · Location ↔ Class code

In plain wordsA contractor's main yard might do roofing and office work, and roofing also happens at their second yard. ISO records each kind of work as its own line under the site where it happens.

A location has many classes, and one class code appears at many locations. Classification is the bridge: it sits under one Location and names one class code with its exposure.

Parent → childrenLocation 1 (Newark) → 91342 Contractors, 41650 Offices
Location 2 (Trenton) → 91342 Contractors
FieldsClassification.LocationNumber, ClassCode, ClassDescription, PremOpsExposure, PremOpsPremiumBasis

Watch: the class itself is not a record, so "all exposure for 91342" means scanning every location.

GLRepeated columns

2 · Classification ↔ Subline

In plain wordsA bar needs regular liability cover and also liquor liability. Instead of two lines, ISO puts both on one wide line, with a separate set of boxes for each type of cover.

One classification row carries exposures for several sublines at once, and each subline covers many classifications.

Sublines on one rowPremises/operations, products/completed ops, liquor, pollution, owners and contractors (OCP), railroad, underground storage tank (UST), electronic data liability (EDL), special protective highway
FieldsSubline, PremOpsProdsClassCode, LiquorClassCode, PollutionExposure, OwnersContractorsClassCode, EDLExposure; child rows ClassificationLiquorCoverage, ClassificationPollutionCoverage

Watch: Classification has 555 fields because of this. One row per subline is the cleaner model.

GLList in one field

3 · Class ↔ Endorsement

In plain wordsEach kind of business comes with a menu of add-ons it's allowed to buy, and the same add-on appears on many menus. ISO stores the whole menu as one long text value.

ExampleClass 91342 → may use CG 20 10, CG 20 37, CG 22 79 …
FieldsClassification.EndtsThatMayBeUsedWithThisClass

Watch: a packed list; it has to be split into a proper class–endorsement table.

GLSchedule text

4 · Endorsement ↔ Location

In plain wordsAn exclusion might say "this policy doesn't cover 12 Main St or Lot 4," and 12 Main St might also be named on another add-on. The address is typed in, not linked to the location on the policy.

At policy level the location is free text on …Detail rows. There are 106 Detail schedules in GL, and 13 types carry a plain Location field.

ExampleExclusion of specific accidents, products, work or location → "12 Main St", "Lot 4"
FieldsExclSpecificAccidentsProdsWorkOrLocationDetail.Location, AccidentLocation, LocationAddress, DesignatedLocation, DescriptionOfPremises

Watch: free text, not a key. The engine must match it to a real location itself.

GLSchedule text

5 · Additional insured ↔ Endorsement

In plain wordsA landlord or general contractor asks to be covered under your policy. The same company can be added on several add-ons, and each add-on can list several companies. Each time, the name is typed in again.

Example"ABC Property Mgmt" on Designated Person or Org (CG 20 26) and on Managers or Lessors of Premises (CG 20 11)
FieldsNameOfPersonOrOrganization (9 types), NameOfAdditionaInsuredPersonOrOrganization (3 types), AddressText

Watch: no party record, so spelling differences make the same company look like two.

GLSchedule text

6 · Vendor ↔ Product

In plain wordsA manufacturer covers the stores that sell its goods. One store sells several products, and one product goes to many stores. Each schedule line pairs store names with product names in text.

ExampleVendor "Home Depot" → ladders, scaffolding
Vendor "Lowe's" → ladders
FieldsAddlInsdVendorsDetail.AdditionalInsured, Products, AddressName

Watch: products are text too, so "ladders" here won't link to the products named on an exclusion.

GLSchedule text

7 · Construction project ↔ Aggregate / exclusion

In plain wordsA contractor can give each job site its own limit so one bad job doesn't use up the whole policy. The same site might also be excluded because it's under a wrap-up program. The site is named separately on each add-on.

Example"Route 9 bridge" → own general aggregate (CG 25 03) and own products aggregate; also named on the wrap-up exclusion
FieldsDesignatedConstrctnProjGeneralAggregateLimitDetail.DesignatedConstructionProject, DesignatedJobSite (3 types), DescriptionOfProject

Watch: projects aren't records, so the engine can't tell which limits share a site.

GLDuplicate types

8 · Endorsement ↔ Attachment level

In plain wordsSome add-ons can apply to the whole policy, one site or one kind of work. ISO doesn't use one add-on with a "level" setting. It makes a separate copy for each level.

ExampleMedical payments exclusion exists under Location and under Classification; additional-insured and aggregate add-ons exist at policy and location level
FieldsExclusionCoverageCMedicalPaymentsLocation, …Classification; AddlInsdOwnersLesseesContrctrsCompldOpsLocLvl vs policy-level forms

Watch: one form can show up under several record names, so form lists need de-duplicating.

CFNumber pointer

9 · Blanket ↔ Building

In plain wordsInstead of a separate limit per building, a business buys one big limit shared by all of them. Each building says "I'm in blanket #1" by number.

ExampleBlanket 1 ($10M building) ← Loc 1 Bldg 1, Loc 1 Bldg 2, Loc 3 Bldg 1
FieldsStructure.BlanketUnitNumber → BlanketRating.UnitNumber; Structure.LocUnitNumber, PersPropertyIncludedInBlanket

Watch: no check. A wrong number silently drops a building from the blanket.

CFNumber pointer ×3

10 · Building ↔ Blanket types

In plain wordsThe same building can be in the main shared limit, a separate shared earthquake limit and a separate shared flood limit, all at once.

ExampleLoc 1 Bldg 1 → property Blanket 1, EQ sublimit blanket, flood blanket
FieldsBlktTypeOfBlanketRating, BlktEQTypeOfBlanketRating; tables BlanketRating, EQSubLimitBlanketRating, FloodCovEndtBlanketRating

Watch: the building's value feeds three totals. Count it once per blanket.

CFBridge record

11 · Building ↔ Occupancy class

In plain wordsA strip mall has a shop, a restaurant and offices. Restaurants also show up in other buildings. Each tenant type gets its own line under the building, and contents insurance hangs off that line.

ExampleLoc 1 Bldg 1 → retail, restaurant, offices
Restaurant also in Loc 2 Bldg 1
FieldsOccupClass.BldgNumber, LocNumber, BlanketUnitNumber; child PersonalProperty

Watch: a tenant's contents can be in a different blanket from the building.

CFNumber pointer

12 · Business income ↔ Building / Location

In plain wordsBusiness income cover pays lost profits while a damaged building is repaired. It can be shared across buildings, and one building can have several kinds. The link is by site and building number.

ExampleBI blanket → Loc 1 Bldg 1 and Loc 2 Bldg 1
Loc 1 Bldg 1 → BI with extra expense, and BI from dependent properties
FieldsBusinessIncome.LocNumber, BldgNumber, BlanketRated; SpecialClassBusnIncome same pattern

Watch: the numbers can disagree with where the row actually sits.

CFCount only

13 · Location set ↔ Coverage group

In plain wordsMany small extra sites can be lumped together under one coinsurance setup. The record says how many sites are in the group, but not which ones.

ExampleAdditional locations, special coinsurance → broad, special and earthquake groups, each pooling "6 locations"
FieldsAdditionalLocationsSpecialCoinsuranceGeneralInformation.MiscLocsCounter, TotalIncLocsLimit; children …BroadCoverage, …SpecialCoverage, …EarthquakeCoverage

Watch: with only a count, nobody can say which sites are pooled.

CFDuplicate types (63)

14 · Endorsement ↔ Insured item

In plain wordsAdd-ons like flood, earthquake or sewer backup can apply to a building, its contents or its lost income, and each of those can carry many add-ons. ISO makes a separate copy of each add-on for every kind of item it can attach to.

ExampleFlood Coverage Endorsement appears under Structure, BusinessIncome, SpecialClass and SpecialClassBusnIncome
Fields63 coverages copied this way, incl. Causes of Loss Basic/Broad/Special, all EQ forms, Flood, Sewer Backup, Green Upgrades, Molten Material, Unmanned Aircraft

Watch: "is flood on this policy?" means checking four places per building.

CFNumber pointer

15 · Loss payee ↔ Building

In plain wordsWhen a bank lends money on a building, it gets paid if the building burns. One bank can lend on many buildings, and one building can have a first and second lender. Each schedule line gives the bank's name plus the site and building numbers.

Example"First National Bank" → Loc 1 Bldg 1, Loc 2 Bldg 1
Loc 1 Bldg 1 → First National (lender), Acme Leasing (contract of sale)
FieldsLossPayableProvisionsDetail.LossPayeeName, Location (int), Building (int), TypeOfLossPayee; Special Class version too

Watch: the bank is typed in each time, and the building numbers aren't checked.

CFSchedule text

16 · Dependent property ↔ Insured location

In plain wordsIf your one key supplier's factory burns, you lose income even though your building is fine. One supplier can feed several of your sites, and one site can rely on several suppliers or customers.

ExampleSupplier "Chip Fab, Austin" → contributes to Loc 1 and Loc 3
Loc 1 → also relies on customer "Big Box DC" (recipient)
Fields…DependentProperties…Detail.SecondaryContributingLocation, SecondaryRecipientLocation, TypeOfDependentProp

Watch: outside properties are text, so the same supplier on two forms isn't linked.

CFFlags per building

17 · Form / deductible ↔ Building

In plain wordsSome forms and deductibles are switched on building by building. A form can be on many buildings, and a building can have many forms. ISO stores this as yes/no switches on each building.

ExampleCP 10 68 attached at Bldg 1 and Bldg 3; Bldg 1 also has a windstorm deductible by location
FieldsFormCP1068AttachedAtBldg, FormCP1065AttachedAtBldg, FormCP0414AttachedAtBuilding; DeductiblesByLocationBldg, WindstormOrHailDeductibleByLocation, TheftDeductibleByLocation

Watch: a new building-level form means a new switch field, not a new row.

What this means for the engine

In plain wordsISO's data never checks that these links line up. If a building says "blanket 2" and there is no blanket 2, or a lender's building number is wrong, nothing complains. We have to check it ourselves.

Guard the number pointers first (9, 10, 12, 15): match BlanketUnitNumber, LocNumber/BldgNumber and loss-payee Location/Building to real records. Next, normalise the typed-in parties, sites and projects (4–7, 16) so the same name is recognised as one thing. Finally, collapse the duplicate endorsement types (8, 14) into one form with an attachment level.
